# ADR-0014: Agents never commit or push; Switchboard-injected tools do

- Status: Accepted (the decision); the mechanisms marked Proposed are unverified
- Date: 2026-10-12
- Decided by: Ender (agents have no commit or push controls; Switchboard tools are injected so that commits carry no
  co-author trailer, "generated by" footer or session ID and look like any other commit; message of 2026-10-12).
  Delegated (agent, 2026-10-12) for every mechanism marked Proposed below.
- Related: FR-GIT-01–09, FR-WS-03, FR-WS-05, FR-POL-03, FR-POL-06, FR-POL-08, FR-EXE-07, NFR-SEC-01,
  [ADR-0003](0003-no-credential-handling.md), [ADR-0004](0004-trust-profiles-no-bypass-flags.md),
  [ADR-0006](0006-worktree-checkpoints-no-blind-replay.md)
- Supersedes in part: [ADR-0006](0006-worktree-checkpoints-no-blind-replay.md), only its clause "The controller never
  pushes to remotes". Its worktree, checkpoint and no-replay decisions stand.

## Context

Coding agents commonly add a co-author trailer, a "generated by" footer or a session link to commits they make. Ender
wants commits that result from Switchboard runs to be indistinguishable from any other commit. The verified research
([R2]) documents no provider setting that controls commit behaviour or attribution, so a plan that depends on switching
those features off per provider would rest on unverified flags (AGENTS.md forbids inventing them). It also requires an
audit trail: the operator must still be able to learn which agent produced which commit.

ADR-0006 and FR-WS-05 said the controller never pushes. Ender's decision requires a push path, so that rule has to
change, safely.

## Decision

1. **Agents cannot commit, move refs or push.** Adapters compile this in through the provider's documented permission
   controls where they exist, and declare where they do not (FR-GIT-01). The agent's environment holds no push
   credentials (FR-GIT-06).
2. **Switchboard injects tools.** For each run the controller supplies a per-run MCP definition offering a `commit` tool
   and, when the context allows it, a `push` tool. The tools are a thin shim that forwards over a per-run local socket
   to the controller, which runs Git outside the agent's process tree (FR-GIT-02). *Proposed:* the shim, the socket and
   the capability token.
3. **Commits look ordinary.** The commit tool writes the commit with the context's configured identity and a sanitised
   message, adds nothing of its own, and strips attribution trailers, footers and identifiers (FR-GIT-04).
4. **History is isolated.** Published commits are created only by the tool onto a separate publish ref per meta-session;
   the internal checkpoint commits and run branches (which do carry a marker and the run ID) are never pushed
   (FR-GIT-08).
5. **Push is policy, default off.** Pushing is allowed only for a context whose policy enables it, only the publish ref,
   under a configured branch prefix, never forced, never the default or checked-out branch (FR-GIT-05).
6. **Detection backs prevention.** Ref snapshots before and after each run catch any commit or ref change the agent
   managed to make; such commits are never published and their content is kept as working-tree changes (FR-GIT-03).
7. **The audit trail lives outside the commit.** Provenance records in the ledger link each commit to the run, provider
   and model (FR-GIT-07). *Rejected:* git notes or trailers, because they travel with the repository.
8. **Fallback.** An adapter that cannot receive the injected channel without a permission-bypass flag uses a
   finalize-only mode where the controller makes the commit after the run (FR-GIT-09). *Proposed.* Cursor is the likely
   candidate if injecting an MCP server turns out to need `--approve-mcps`, which [R2] lists as a separate switch and
   FR-POL-03 treats as a bypass flag (unverified).

## Alternatives considered

- **Let agents commit, then rewrite history to strip trailers.** Rejected as the primary design: it relies on every
  provider's commit behaviour, rewrites pushed history if the agent pushed, and cannot undo a push. Kept only as the
  detection-and-normalisation backstop (item 6).
- **Switch off each provider's attribution setting.** Rejected as the only control: no such setting is in [R2], settings
  change with CLI versions, and it would not stop an agent running `git commit` by hand.
- **A `commit-msg` Git hook that strips trailers.** Rejected as a control: an agent with a shell can bypass hooks.
  Usable as a guard against accidental provider-internal commits (TDD §3.10).
- **Only a controller-made commit at the end of every run (no tool).** Kept as the fallback. It gives the agent no way
  to split work into several commits or write its own message, which is why Ender's tool-based design is preferred.

## Consequences

- A new component, the Git Publisher (COMP-GIT), and a new trust boundary (agent to injected tool, TB-7).
- Provenance replaces in-commit markers. If the operator later rebases or squashes published commits the SHA link breaks,
  so records also keep tree hash and patch ID (best effort).
- The sanitiser is a pattern list and cannot be complete; an agent can still write attribution into file contents or a
  message in words the patterns miss. Residual risk R-14.
- Removing provider attribution may interact with a provider's terms. That has not been reviewed; it belongs in the
  compliance manifest review (FR-POL-07, NFR-COMP-01, risk R-16).
- Keeping push credentials away from a same-user agent shell needs either a container environment or a shell-less
  profile (FR-GIT-06). Until M10, push-enabled contexts are limited accordingly.
- The checkpoint identity in `src/workspace/git.ts` (`Switchboard <switchboard@localhost>`) stays, because checkpoints
  are internal. Published commits use a different, operator-configured identity.

## Revisit when

A provider documents commit or attribution controls (then add them to the adapter table), the finalize-only fallback
turns out to be the common case, or an orchestrator needs to push to protected branches.
