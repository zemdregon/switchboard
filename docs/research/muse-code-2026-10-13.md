## Evidence quality

Meta's official page ([dev.meta.ai/docs/muse-code](https://dev.meta.ai/docs/muse-code)) appears in search results,
described as "Meta's coding agent for the terminal and CI, built for Muse Spark, with approvals, sandboxing, sessions,
and multi-agent orchestration". The page could not be fetched in this session (the scraping tool does not support the
site), so **nothing below was read from Meta's documentation**. The facts come from two third-party sources, both
fetched on 2026-10-13:

1. A user report in a GitHub issue on another project
   ([stablyai/orca#19672](https://github.com/stablyai/orca/issues/19672), comment of 2026-09-13), stating what the
   commenter verified against `Muse Code 1.2.1 (1.2.1-R2847.1)` on macOS arm64. The issue text itself quotes
   `Muse Code 1.0.3`. These are one person's observations.
2. The `muse-codes` Rust SDK ([docs.rs](https://docs.rs/muse-codes/latest/muse_codes/), crate 1.4.7, Apache-2.0),
   whose types are said to be derived from captured real CLI output taken in a credential-free `--provider echo` mode.

Every item is therefore an **Assumption** until checked against Meta's documentation and an installed binary
(ROADMAP Q-27 and the M4 task that breaks down this adapter). A search snippet from a tutorial page shows
`muse --version` as
`Muse Code 0.1.0`, so the CLI's versions move quickly (compare R-1).

## What the sources report

| Topic | Reported (unverified) |
| --- | --- |
| Binary and launch | `muse` (interactive TUI) and `muse exec [OPTIONS] [PROMPT]` (headless, one turn, then exits). Installs to `~/.local/bin/muse` with a self-updating launcher; `MUSE_NO_AUTO_UPDATE=1` pins the version (it otherwise updates hourly) |
| Structured output | `muse exec --json` writes a JSONL event stream on stdout: envelope records for command intake, run lifecycle, task lifecycle and streamed output. A terminal record such as `{"kind":"run_terminal","terminal":"completed","text":"...","reason":null}` marks the end. The SDK deserialises unknown payload kinds as `Unknown`, so the set of kinds is not fully known |
| Exit codes | `0` turn completed, `1` failed or aborted (including `--max-model-steps` exhausted), `2` usage error, `130` SIGINT, `143` SIGTERM. **Exit 0 does not mean the work succeeded**; gate on the stream's terminal record and the controller's own checks |
| Approvals and sandbox | On by default. `--approval-mode untrusted\|on-request\|never` (default `on-request`); `--sandbox-network restricted\|enabled\|proxy-only` (default `proxy-only`); `--disable-approval`, `--disable-sandbox`, `--trust-workspace` |
| Bypass | `--yolo` = `--disable-approval --disable-sandbox --trust-workspace` in one. It is a flag of `exec` and must come after the subcommand: `muse exec --yolo "..."` |
| Worktrees | `-w, --worktree off\|create\|existing`. `create` makes its own worktree under `<repo>/.muse/worktrees/` and leaves files behind; the commenter recommends `off` when the host supplies the worktree. With `off`, it reportedly does not follow a worktree's `.git` file up to the main repository |
| Cost cap | `--max-model-steps <N>` |
| Workspace trust | In an untrusted workspace the CLI skips the project rules file and disables subagent delegation, with only stderr warnings. Trust is stored in `~/.config/muse/trust.json` |
| Project rules and skills | Reads `AGENTS.md`, falling back to `CLAUDE.md` and similar; skills from `.agents/skills/`, `~/.agents/skills`, `$XDG_CONFIG_HOME/muse/skills`, and also `~/.claude/skills` and `~/.codex/skills` |
| Settings and credentials | `~/.config/muse/settings.json` (must contain `"schema_version": 1`), credentials in `~/.config/muse/auth.json`, session logs under `~/.local/share/muse/sessions/` as append-only JSONL |
| Auth | Precedence reported as `META_API_KEY` environment variable, then a stored key, then a stored browser session. `muse login` is an OAuth device-code flow. A key can be stored with `muse auth set --api-key-stdin` (the CLI refuses a key as a flag value) |
| Resume | Sessions exist and Orca's integration mentions resume; the flag spelling was not reported in the sources read |
| Latency | One user measured 10.3 to 15.9 s to first output |
| Other | `--no-foreign-personal-context` (`exec` only); a credential-free `--provider echo` mode exists, per the SDK, which is useful for fixtures |

## Implications for Switchboard (Proposed)

- **Fits the existing adapter model.** A subprocess with JSONL output, like Codex (FR-ADP-04, FR-ADP-11). A recorded
  fixture set can be captured from the `echo` provider without any login.
- **Credentials (ADR-0003, FR-AUTH-01).** The adapter must rely on the operator's native login (`muse login`) and must
  not pass `META_API_KEY`: the environment allowlist (FR-EXE-07) excludes it, and `doctor` tells the operator to log in
  natively. If the operator can only use an API key, that is a Q-27 follow-up, not something the controller handles.
- **Bypass flags (ADR-0004, FR-POL-03).** `--yolo`, `--disable-approval`, `--disable-sandbox` and `--trust-workspace`
  join the argv audit's forbidden list unless an approved `privileged` scope calls for them.
- **Untrusted profiles.** Muse's defaults (approvals and sandbox on, workspace untrusted skips project rules) look
  compatible with FR-POL-04, but whether `--approval-mode`/sandbox settings can be compiled into the five profiles, and
  whether trust is granted by a prompt that blocks a headless run, is unknown.
- **Worktrees.** Pass `-w off`; the controller owns worktrees (FR-WS-01). Never use `create` or `existing`.
- **Git writes (FR-GIT-01).** No per-command deny control was reported, so the adapter declares `none-documented` until
  one is found, as for Codex.
- **Success.** Exit code and the `run_terminal` record are not proof of success (BR-16 verification stays the judge).
- **Version gating (ADR-0009).** Self-updating hourly makes the version a moving target; the adapter sets
  `MUSE_NO_AUTO_UPDATE=1` (if confirmed) and revalidates on version change.
- **Project rules.** Muse reads `AGENTS.md` and `CLAUDE.md` and other tools' skill directories in the home directory,
  which is a repository-supplied and ambient-config input to control under untrusted profiles (FR-POL-04, FR-POL-08).
- **Capacity.** Whether the plan reports usage, limits or reset times is unknown (FR-CAP-01 records only what is
  reported). Model names (the Muse Spark family) are not stated as fact in the specs; they come from the model registry
  (FR-ADP-05).

## Update 2026-10-13 (T4.70): Meta's documentation read

Later on 2026-10-13 the pages under <https://dev.meta.ai/docs/muse-code> (overview, auth, permissions, interactive,
rewind, configuration, extending, changelog) were fetched with WebFetch; the scraping tool still refuses the site and
`https://meta-models.github.io/muse-code-sdk` only redirects. The earlier "could not be fetched" statement above is
kept as written; the row-by-row results are in [TDD §4.8](../design/TDD.md#48-muse-code-m4). Points that change this
note: headless resume is `muse exec --session-id <uuid>` (not the interactive `muse resume`); `--sandbox-network` takes
`restricted`, `proxy-only` and `unrestricted` (`enabled` is a deprecated alias); a first headless run in an untrusted
workspace stops with a message naming `--trust-workspace`; trust also gates hooks; MCP servers come from the
`mcp_servers` settings block or the per-run `-c key=value`; no auth status command and no per-command Git deny control
is documented. Not found in Meta's pages: `MUSE_NO_AUTO_UPDATE`, hourly self-update, the `-w` values, the
`run_terminal` line and the trust file location (still third-party reports). The changelog text prints the command
name `tbh` in some entries (for example `tbh -w`, `tbh exec`); treat the binary name as `Unverified: T4.71`.
