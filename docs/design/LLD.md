## 1. Data model

Persistence is one SQLite database in WAL mode, single writer ([ADR-0005](../adr/0005-sqlite-ledger.md), SRS §6).
Conventions:

- **IDs** are ULID text with a type prefix: `sess_`, `run_`, `evt_`, `art_` (fixed by the brief); other prefixes are
  Proposed: `dec_`, `ckp_`, `rte_`, `apv_`, `adv_`, `use_`, `pbd_` (provider binding, added in M2 T2.4). IDs are
  generated by the controller, never by providers (FR-SES-01).
- **Timestamps** are `TEXT` in UTC ISO-8601 with millisecond precision (`2026-10-12T09:30:00.123Z`), set from an
  injectable clock. Lease/expiry comparisons use the same format.
- **JSON columns** hold validated JSON text (`CHECK (json_valid(col))`). Prompts and provider output do not live in JSON
  columns; large payloads go to artifacts (FR-TEL-03).
- All tables are `STRICT`. Foreign keys `ON`. `PRAGMA journal_mode=WAL; synchronous=FULL` (Proposed: durability over
  speed for crash safety, NFR-REL-01); `busy_timeout` set although only one writer exists.
- **Append-only** (enforced by `BEFORE UPDATE/DELETE` triggers that `RAISE(ABORT)`): `run_event`, `decision`,
  `workspace_checkpoint`, `usage_observation`, `route_decision`, and (M11) `inner_call` (FR-SES-05, FR-RTE-03, FR-CAP-01,
FR-INN-15). **Update-once**
  (pending to decided): `approval`. **Mutable current-state**: `meta_session`, `run`, `provider_health`,
  `adapter_version.validated_*`, (M11) `inner_task_state`, and `artifact.deleted_at` only. Retention GC removes artifact
  files and worktrees and
  sets `artifact.deleted_at`; it never deletes `run_event` rows (Assumption).

```sql
  breaker_until     TEXT,
  consecutive_failures INTEGER NOT NULL DEFAULT 0,

  last_failure_code TEXT,

CREATE TABLE route_decision (           -- append-only (FR-RTE-03); M2 writes eligibility only, M7 adds scores

  reasons_json    TEXT NOT NULL CHECK (json_valid(reasons_json)),

  run_id        TEXT NOT NULL REFERENCES run(id),  -- the run that requested it; covers its meta-session (§3.1)
  scope_json    TEXT NOT NULL CHECK (json_valid(scope_json)),   -- canonical privileged_scope (§3.1)
  scope_hash    TEXT NOT NULL,          -- SHA-256 over client, meta-session and scope (§3.1, v2)
  status        TEXT NOT NULL CHECK (status IN ('PENDING','APPROVED','DENIED','EXPIRED')),
```

Triggers (shape, one per append-only table): `CREATE TRIGGER run_event_no_update BEFORE UPDATE ON run_event BEGIN SELECT
RAISE(ABORT,'append-only'); END;` and the same for `DELETE`. An analogous guard allows `approval` to change only from
`PENDING`. The controller never writes `EXPIRED` (no expiry: WF-7,
[ADR-0017](../adr/0017-approved-privileged-scope-bypass.md)); the value stays in the `CHECK` only so the M1 schema needs
no migration.

**Operator cancel requests (M1, Proposed).** `runs cancel` records a request as append-only `run_event` rows of type
`operator_cancel_requested` (payload `requested_by`, `reason`), later followed by `operator_cancel_applied`
(`request_event_id`, `state_after`, `applied_by`) or `operator_cancel_rejected` (`request_event_id`, `detail`). The daemon
and startup reconciliation apply pending requests. No table was added because `run_event` is already append-only and
transactional with state changes, the CLI works with no daemon, and a pending request is just a request event without a
matching applied or rejected event. This is Delegated, not owner-approved; it stays inside ADR-0005 (no new store).

**M9 additions (Proposed).** Project definitions live in the configuration file (operator) or in the ledger (projects an
orchestrator created, FR-PRJ-10) and are snapshotted into `run.policy_snapshot_json`; the ledger adds the project ID, one
append-only provenance table and one append-only project-revision table, in a forward migration (ADR-0005). `git_commit`
and `project_revision` join the append-only list above.


New `run_event.type` values (M9): `environment` (create, start, stop, remove; M10), `git_commit`, `git_push`,
`git_policy_violation`, `git_tool_denied`. Payloads are bounded and hold no message text, only counts, SHAs and rule IDs.
Both new tables get the same `BEFORE UPDATE`/`DELETE` guards as the other append-only tables.

**M11 additions (Proposed).** One forward migration (ADR-0005) adds the append-only `inner_call` table and the mutable
`inner_task_state` table (DDL in [§13.3](#133-data)), adds `pr_draft` to the `artifact.kind` check, adds `inner_agent` to
the `usage_observation.source` check (FR-INN-15), and adds two columns to `git_commit` (§12.7). SQLite cannot alter a
`CHECK`, so the two checks are widened by the migration runner's table-rebuild step. `route_decision.features_json` keeps
its column; only its content gains per-feature `source`, `model_id` and `template_version` (§13.6, `route_features`).
The inner agent's entities are therefore `inner_call` (history) and `inner_task_state` (current suspension state per
task), plus the columns above; no inner prompt or response body is stored anywhere (FR-INN-16).

## 2. Adapter contract

Satisfies FR-ADP-01 (probe, auth preflight, compile, parse, resume, cancel). Adapters are pure with respect to I/O
except `probe`/`authPreflight`, which execute the provider binary through a supervisor-provided `ProbeRunner` (so tests
inject fakes). Adapters never read credential files (FR-AUTH-01).

```ts
export type ProviderId = 'claude' | 'codex' | 'grok' | 'antigravity' | 'cursor' | 'opencode' | 'kimi' | 'muse' | 'fake';
export type TrustProfile = 'inspect-untrusted' | 'edit-untrusted' | 'test-sandboxed'
                         | 'trusted-development' | 'privileged';

export interface ProviderAdapter {
  readonly id: ProviderId;
  readonly transports: readonly Transport[];
  /** FR-GIT-01 declaration (M2, T2.2), reported by list_capabilities. */
  readonly gitWriteControl: GitWriteControl;

  /** FR-ADP-02 steps 1-5: binary, version, command, output formats, required flags. No auth, no model call. */
  probe(runner: ProbeRunner): Promise<ProbeResult>;
  /** Provider's own status command or a harmless headless call; never reads credentials (FR-AUTH-02). */
  authPreflight(runner: ProbeRunner): Promise<AuthResult>;
  /** Pure. Returns Ineligible (never a downgraded profile) when the profile cannot be satisfied (FR-POL-02). */
  compile(request: CompileRequest, profile: ResolvedProfile): Invocation | Ineligible;
  /** One stdout line (JSONL) or one ACP message -> zero or more events. Stateful via ParseState. */
  parseEvent(input: string | AcpMessage, state: ParseState): NormalizedEvent[];
  /** Folds the event stream plus exit info into the run result. */
  extractResult(events: readonly NormalizedEvent[], exit: ExitInfo): RunResult;
  /** Invocation fragment that continues a native session (FR-SES-03). Pure. */
  resumeArgs(binding: NativeBinding, request: CompileRequest, profile: ResolvedProfile): Invocation | Ineligible;
  /** Optional graceful cancel (e.g. ACP cancel message); supervisor still enforces SIGTERM/SIGKILL. */
  cancel?(handle: TransportHandle): Promise<void>;
  /** Maps evidence to one taxonomy code (section 4); unknown evidence -> OUTPUT_PROTOCOL_ERROR or TOOL_FAILURE, never success. */
  classifyFailure(evidence: FailureEvidence): FailureClassification;
}

export type Transport = 'subprocess-jsonl' | 'acp-stdio' | 'local-service'; // last deferred (FR-EXE-04)

/** FR-GIT-01 (Proposed shape, implemented in M2). */
export interface GitWriteControl {
  kind: 'provider-deny-rules'     // compile() passes the provider's documented deny controls for Git writes
      | 'none-documented';        // the provider documents none; FR-GIT-03 and FR-GIT-06 are what remains
  detail: string;                 // mechanism and source, or why none is documented; known limits
  remainingControls: string[];    // requirement IDs, e.g. ['FR-GIT-03', 'FR-GIT-06']
}

export interface ProbeResult {
  binaryPath: string; binaryVersion: string | null;
  steps: Array<{ step: 'binary'|'version'|'command'|'output_format'|'flags'|'smoke'; ok: boolean; detail?: string }>;
  modelsListed?: string[];              // feeds the model registry (FR-ADP-05)
}
export type AuthResult =
  | { state: 'OK' }
  | { state: 'AUTH_REQUIRED'; loginCommand: string }   // names the native command for the operator
  | { state: 'UNKNOWN'; reason: string };              // treated as ineligible (NFR-SEC-06)

export interface CompileRequest {
  runId: string; objective: string; constraints: string[];
  workspace: { cwd: string; writable: boolean };
  model?: string; verificationCommands?: string[][];
  handoff?: { bundleArtifactId: string };                // M5
  bypassApproved?: boolean;  // T3.17, optional mirror of ResolvedProfile.bypassApproved (the carrier); adapters accept
                             // either, never compute it; the lifecycle sets the profile's value (§3.1 "Bypass")
}
export interface ResolvedProfile {                       // from COMP-POL, snapshot stored on the run
  name: TrustProfile; fileAccess: 'read-only'|'worktree'|'scoped';
  shell: 'none'|'allowlist'|'broad'|'scoped'; shellAllowlist?: string[];
  network: 'off'|'allowlist'|'policy'|'scoped'; networkAllowlist?: string[];
  repoConfig: 'disabled'|'approved-only'|'allowlisted'|'scoped';
  bypassApproved: boolean;                               // true only per §3.1 "Bypass" (FR-POL-03, ADR-0017)
  privilegedScope?: { scope: PrivilegedScope; scopeHash: string; approvalId: string };  // privileged only (§3.1)
}

export interface Invocation {
  transport: Transport;
  argv: string[];                       // argv[0] = absolute executable path from probe; never a shell string
  env: Record<string, string>;          // built from envAllowlist + adapter-declared vars only (FR-EXE-07)
  envAllowlist: string[];               // names, for audit and tests
  cwd: string;                          // run worktree (canonical)
  stdin?: { kind: 'text'; value: string } | { kind: 'none' };
  outputFormat: 'json' | 'jsonl' | 'acp';
  timeouts: { wallClockMs: number; idleMs: number; killGraceMs: number };
  policyFlags: string[];                // every security-relevant flag, for the bypass-flag audit
  expectedExitCodes: number[];
  maxLineBytes: number;
}
export interface Ineligible {
  ineligible: true;
  reason: 'PROFILE_UNSUPPORTED' | 'VERSION_UNVERIFIED' | 'NO_MANIFEST' | 'AUTH_REQUIRED' | 'CAPABILITY_MISSING';
  detail: string;                       // surfaced via explain_route and FR-MCP-05
}
```

**Provider ids.** Two id spaces exist (Proposed, M2; the single mapping table is `CONFIG_TO_ADAPTER_ID` in
`src/routing/collect.ts`). Config files and `providers.<id>` use the provider names from the roadmap; the adapter
contract, the ledger and MCP tools use the `ProviderId` above. They differ for four providers:

| Config provider id | Adapter `ProviderId` |
| --- | --- |
| `claude-code` | `claude` |
| `grok-build` | `grok` |
| `kimi-code` | `kimi` |
| `muse-code` | `muse` |
| `codex`, `antigravity`, `cursor`, `opencode` | the same string |

`fake` is a test adapter with no config id.

**Ineligible to failure code.** The adapter reasons map to the codes in §4 per
[FRD BR-3](../requirements/FRD.md#3-business-rules): `AUTH_REQUIRED` gives `AUTH_REQUIRED`; `VERSION_UNVERIFIED` gives
`ADAPTER_VERSION_UNVERIFIED`; `NO_MANIFEST`, `PROFILE_UNSUPPORTED` and `CAPABILITY_MISSING` give `ELIGIBILITY_NONE`.

`NormalizedEvent` (observable facts only, NFR-PRIV-02; no provider reasoning text):

```ts
export type NormalizedEvent =
  | { kind: 'session_bound'; nativeSessionId: string; model?: string; backingProvider?: string }
  | { kind: 'tool_call'; tool: 'read'|'edit'|'shell'|'other'; name: string; target?: string; denied?: boolean }
  | { kind: 'message'; role: 'assistant'; text: string }               // bounded; final-visible text only
  | { kind: 'usage'; source: 'provider_reported'; metrics: Record<string, number|string|null> }
  | { kind: 'rate_limit'; resetAt?: string; reportedCategory?: string }
  | { kind: 'permission_denied'; tool: string }                         // -> PERMISSION_BLOCKED
  | { kind: 'sandbox_violation'; detail: string }                       // -> SANDBOX_VIOLATION
  | { kind: 'provider_error'; category: string; message: string }
  | { kind: 'result'; ok: boolean; summary?: string }
  | { kind: 'unknown'; rawType: string };                               // counted, recorded, never trusted
```

Parsing rules: unparseable framing yields no event and the supervisor ends the run with `OUTPUT_PROTOCOL_ERROR`
(NFR-SEC-06). Fields are taken from structured JSON only, never regex over free text (FR-ADP-04). `FailureEvidence`
bundles `{events, exit, stderrTail (bounded), timedOut, cancelled}`. A central bypass-flag audit runs over
`Invocation.policyFlags` and `argv` before spawn (FR-POL-03). Per-adapter parsing specifics: to be detailed in M2
(Claude) and M4 (others).

**M9 additions to the adapter contract (Proposed).** Each adapter also declares how it meets FR-GIT-02. (The FR-GIT-01
part, first drafted here as `gitWrites: 'denied-by-provider-rules' | 'no-shell-profiles-only' | 'undeclared'`, was
implemented in M2 as `gitWriteControl` above; `undeclared` became `none-documented` because FR-GIT-01 requires the
adapter to declare the absence.)

```ts
export interface GitCapabilities {
  /** FR-GIT-02: can the per-run injected tool channel be supplied without a bypass flag (FR-POL-03)? */
  commitChannel: 'injected' | 'finalize-only' | 'none';
  /** Pure: the MCP definition for the shim, in the provider's own per-run form; never written to global config (FR-POL-08). */
  channelArgs?(shim: ShimSpec, request: CompileRequest, profile: ResolvedProfile): Pick<Invocation, 'argv' | 'env'> | Ineligible;
}
export interface ShimSpec { command: string[]; socketPath: string; toolNames: ('commit' | 'push')[]; }
```

`compile` appends the deny rules and, for `commitChannel: 'injected'`, the `channelArgs` result. An adapter with
`commitChannel: 'none'` is ineligible for write-capable profiles on a context unless the operator opts in to
finalize-only mode (BR-30). The bypass-flag audit (FR-POL-03) treats any flag whose only purpose is approving the
injected server as a bypass flag. Which providers fall in which category is **to be verified** per adapter
([TDD §3.10](TDD.md#310-git-commits-attribution-and-publication)).

### 3.1 Privileged scope (M3)

client configured `privileged_approval: "not_required"` is admitted without the operator's `approve` (**Client policy**
below, [ADR-0019](../adr/0019-per-client-privileged-approval.md)), and the lifecycle no longer refuses every
`privileged` run at dispatch: the adapter's compile decides ([ADR-0018](../adr/0018-claude-bypass-omits-restricted.md)
for Claude Code bypass runs).

```ts
export interface PrivilegedScope {
  files: { access: 'read-only' | 'worktree' };
  shell: { mode: 'none' | 'broad' } | { mode: 'allowlist'; allowlist: string[][] };
  network: { mode: 'off' | 'on' } | { mode: 'allowlist'; hosts: string[] };

```

Meaning of each value, and how it lines up with the profile fields of `ResolvedProfile` (§2, `src/policy/profiles.ts`):

| Dimension | Values | Meaning | `ResolvedProfile` field |
| --- | --- | --- | --- |
| `files.access` | `read-only`, `worktree` | Read only, or edits confined to the run's worktree. There is no wider value: a `privileged` run still works in a worktree (FR-WS-01) | `fileAccess` (same values) |
| `shell.mode` | `none`, `allowlist`, `broad` | No shell; only the listed commands; any command | `shell`, `shellAllowlist` (same values) |
| `shell.allowlist` | argv arrays | Each entry is one exact argv (program and arguments); no wildcard, no shell string | `shellAllowlist` |
| `network.mode` | `off`, `allowlist`, `on` | No network; only the listed hosts; unrestricted | `network`, `networkAllowlist`; `on` has no profile counterpart (the profile value `policy` is not offered in a scope, because it names no behaviour by itself) |
| `repository_config.mode` | `disabled`, `approved`, `enabled` | Repository-provided hooks, MCP definitions and agent instructions not loaded; only those the operator's configuration approves; all loaded | `repoConfig` `disabled`, `approved-only`, and a scope-only `enabled` (wider than `allowlisted`) |
| `bypass` | boolean, default `false` | The provider's bypass flag is requested; emitted only under the conditions in **Bypass** below | `bypassApproved` (set from the approval, never from the request) |

*Note (2026-10-13, owner decision 26, Q-37, [ADR-0021](../adr/0021-repository-config-in-approved-bypass-runs.md);
T3.19):* `approved` and `enabled` are compilable only in an approved bypass run (`bypass: true` and the run's
`bypassApproved`). The Claude adapter then omits `--safe-mode`, keeps `--strict-mcp-config` for `approved` and omits
it for `enabled`; the Git deny rules and the worktree are unchanged. Without that approval, and for a Codex scope (its
bypass is undocumented), they remain `Ineligible: CAPABILITY_MISSING`. Flag behaviour unverified (R-41).

**Validation** ([FRD §7.1](../requirements/FRD.md#71-delegate_task), in table order): a malformed scope fails schema
validation (V1, `INVALID_REQUEST`, `details.field` naming the offending path): every dimension is required, unknown keys
are refused at every level, `shell.allowlist` is present exactly when `shell.mode` is `allowlist` and `network.hosts`
exactly when `network.mode` is `allowlist` (the JSON Schema above cannot say "iff", so T3.3 checks it in code as part
of V1). `privileged` above the client's ceiling is `PERMISSION_BLOCKED` (V5, BR-13) whether or not a scope is present;
then V13: `privileged` without a scope, or a scope with any other profile, is `INVALID_REQUEST`
(`details.field = "privileged_scope"`). Entries are stored and shown verbatim, so they must not contain secrets; they are
never written to MCP envelopes or logs.

**Compilation.** The adapter compiles a `privileged` run from the scope in its policy snapshot, not from a configured
profile: `privileged` has no `profiles.<name>` override (T3.2). Each dimension maps to the provider's native control
(T3.5, T3.6). A dimension the provider cannot express makes the provider `Ineligible` for the run with a reason naming
the dimension (FRD BR-3); it is never dropped, widened or narrowed silently. The FR-GIT-01 Git write deny rules apply to
every compiled `privileged` invocation whatever the scope says; no scope value permits a Git write by the agent. If a
bypass flag would override those rules on a provider, that is R-26, not something a scope can grant.

**Canonical form and hash.** At admission (FRD T2), with defaults filled (`bypass` present, `false` when omitted):

```text
scope_json = canonicalJson(privileged_scope)                       // sorted keys, as request_hash (§10);
                                                                   // list order kept as given
scope_hash = hex(SHA-256(canonicalJson({ "v": 2,
                                         "client_id": run.client_id,
                                         "meta_session_id": run.meta_session_id,
                                         "scope": privileged_scope })))
```

`v: 1` (the hash over the run ID and `request_hash`) was never implemented and is withdrawn. The `v: 2` hash binds the
approval to one MCP client, one meta-session and one canonical scope (owner decision 17), not to one run, so it is the
same for every run of that meta-session that uses that scope, and different for any other client, meta-session or
scope. The run row, the `PENDING` approval row (`run_id` = this first run, `scope_json`, `scope_hash`, `requested_at`)
and the first `run_event` are written in one transaction; the policy snapshot records `privilegedScope` with the same
`scopeHash` and the approval's `approvalId`. An idempotent replay (§10) returns the existing run and creates no second
approval row. No schema change is needed: `approval.run_id` names the run that requested the approval, and the
meta-session and client are read from that run.

**Lookup.** A meta-session has at most one approval row in M3, because only `delegate_task` creates one and it always
starts a new meta-session. The approval of a meta-session is found by joining `approval.run_id` to `run` with the
meta-session ID and client ID (Proposed: T3.3 may add an index in a forward migration if the query needs one).

- `delegate_task` with `privileged` always creates a new meta-session, so it always creates a new `PENDING` row and an
  AWAITING_APPROVAL run, even when an identical scope was approved for another meta-session.
- `continue_task` whose resolved profile is `privileged` (requested, or defaulted from the previous run, FRD C4) looks
  up the meta-session's approval for the calling client. If it is `APPROVED`, the continuation takes the approved
  scope as is: `continue_task` has no scope input, so it cannot widen, narrow or otherwise change the scope (FRD C7).
  The new run is admitted to QUEUED (FRD T1) with `privilegedScope` copied from the approval (`scope`, `scopeHash`,
  `approvalId`) and a `run_event` naming the approval; no new row is written. If the row is `PENDING`, `DENIED` or
  absent, or the caller is a different client, the request is `INVALID_REQUEST` (C7) and nothing is written.
- A different scope means a new `delegate_task`, and therefore a new meta-session and a new `PENDING` approval; a
  different client never matches.

**Approve.** The operator reviews the scope and hash with `runs show`, then runs `approve <run_id>` (operator CLI
only, FR-OPS-02) on the run that requested the approval. It recomputes the hash from that run's `client_id`,
`meta_session_id` and the stored `scope_json`, and writes `APPROVED`, `decided_at` and `decided_by` only if the run is
AWAITING_APPROVAL, the row is `PENDING` and the recomputed hash equals `scope_hash`; otherwise it is a CLI error and
nothing changes. `approve` on a later run of the meta-session is a CLI error: it is not AWAITING_APPROVAL and has no
row of its own. `deny` writes `DENIED` and the run ends CANCELLED (WF-7). No MCP tool, timer or client ceiling
approves, and no configuration value does except the per-client `privileged_approval` setting below. An approval never
expires and is never revoked automatically (owner decision 17); a manual revoke is ROADMAP Q-30.

**Client policy (2026-10-13, owner decision 22; Delegated realisation, [ADR-0019](../adr/0019-per-client-privileged-approval.md)).**
Each `mcp_clients[]` entry has `privileged_approval`: `"required"` (default) or `"not_required"`, the latter valid only
with a `privileged` ceiling ([TDD §3.1](TDD.md#31-configuration)). For a `"required"` client everything above holds
unchanged. For a `"not_required"` client a `privileged` `delegate_task` passes the same validation (V1, V5, V13), the
same canonical form and the same `v: 2` hash, and is then admitted by FRD T1 to QUEUED instead of T2. In the admission
transaction the controller writes the approval row as for T2 and decides it at once: `status = 'APPROVED'`,
`decided_at` = admission time, `decided_by = "client_policy:<client_id>"`; the first `run_event` is the T1
`state_transition` naming the approval (`approval_id`, `approval: "client_policy"`), followed by an `approval_decided`
event (`approval_id`, `status`, `reason: "client_policy"`). No other check is relaxed: **Lookup**, C7 continuations and
**Bypass** treat the row like an operator approval; the FR-GIT-01 deny rules and the run's worktree (FR-WS-05) apply.
`approve` and `deny` refuse such a run (it is never AWAITING_APPROVAL) and name the client policy. The envelope shows
`approval.status` `APPROVED` and never `decided_by`.

**Bypass.** Before compiling any `privileged` run, COMP-POL loads the approval named by the snapshot's `approvalId` and
sets `bypassApproved = true` only if: the row is `APPROVED`; its `scope_hash` equals the snapshot's `scopeHash` and the
hash recomputed from this run's `client_id`, `meta_session_id` and snapshot scope; and the approved scope has
`bypass: true`. Any mismatch fails the run `PERMISSION_BLOCKED` before spawn, with a `run_event` naming the mismatch
(no process, no flag). With `bypassApproved` false the adapter compiles `privileged` without a bypass flag. The argv
audit (T3.17) independently refuses any `BYPASS_FLAGS` entry unless the profile is `privileged`, `bypassApproved` is
true and the snapshot's scope sets `bypass` (the lifecycle passes the run's resolved profile and `bypassApproved` to
`startAdapterRun`, so the audit sees the same values the compile did). The compiled `policyFlags` are recorded in the
run's events, so every bypass run's invocation and the approval it ran under are in the audit trail.

**Listing (Proposed, Delegated, 2026-10-13).** `list_capabilities` lists `privileged` in a provider's
`supported_profiles` when its adapter compiles **any** scope of a small representative set, all with `bypass: false`
(listing never compiles with `bypassApproved`): (1) the narrowest scope (`read-only` files, shell `none`, network `off`,
repository configuration `disabled`); (2) `worktree` files, shell `none`, network `on`, repository configuration
`disabled`; (3) `worktree` files, shell `broad`, network `off`, repository configuration `disabled`. No single scope
compiles for both M3 adapters (Claude Code has no network control, so it compiles network `on` only; Codex cannot
disable commands, so it needs shell `broad` with network `off`), so the narrowest scope alone would list `privileged` for
nobody. A listed `privileged` means "this provider compiles at least one privileged scope here"; each request's own
scope is still compiled at dispatch, where an `Ineligible` ends the run with its BR-3 code. Code:
`REPRESENTATIVE_PRIVILEGED_SCOPES` in `src/mcp/server.ts`.

**What is shown where.** The envelope (`get_run`, `delegate_task`, `continue_task`, `cancel_run`) carries only
`approval.status` and `approval.requested_at` for a `privileged` run; it never contains the scope content, the hash or
`decided_by` (FR-MCP-04). `runs show` (operator CLI) shows the full scope, the `bypass` value, the scope hash, the
approval decision and, for an approval, every run of the meta-session that ran under it.

**Implementation notes (T3.3, Proposed, Delegated).** Code: `src/policy/scope.ts` (schema, list checks, canonical
form, hash, spelling maps), `src/lifecycle/lifecycle.ts` (admission), `src/ledger/repo.ts` (approval helpers).

- Spellings: neither enum is renamed. A `privileged` snapshot keeps `scoped` in the four scalar fields and the scope in
  its own spellings; `src/policy/scope.ts` maps them (`on` and `enabled` have no profile value; `approved` is
  `approved-only`) for the adapters (T3.5, T3.6).
- `network.hosts` entries must match a bare host-name pattern (no scheme, port, path or wildcard).
- V11 for `privileged` defers the adapter's compile verdict to dispatch ([FRD V11](../requirements/FRD.md#71-delegate_task)),
  because `bypassApproved` is known only there. *Changed 2026-10-13 (T3.18, owner decisions 19 and 22):* the earlier
  blanket dispatch refusal of every `privileged` run ("privileged compile not available until T3.5/T3.6") is removed.
  After the **Bypass** check passes, the lifecycle appends a `privileged_dispatch` event (`approval_id`,
  `bypass_approved`) and hands the snapshot with that `bypassApproved` to the preflight eligibility compile and the
  LEASED compile; an adapter `Ineligible` ends the run with its BR-3 code (FRD T8 or T10), as for any profile. A stored
  `bypassApproved` is never trusted: the lifecycle resets it to `false` for every run before the check.
- Cancelling a run in AWAITING_APPROVAL closes its `PENDING` row as `DENIED` in the same transaction (ROADMAP Q-15
  default): `decided_by` is `cancel_run` for the MCP tool and the requesting OS user for `runs cancel`, plus an
  `approval_closed` `run_event` (approval ID and status only).
- The §1 guard lets any column change while a row is `PENDING`. The repo helper updates only `status`, `decided_at` and
  `decided_by`; the hash re-check (C7 here, `approve` in T3.4) catches a scope rewritten without its hash, but not a
  writer with ledger access who rewrites both.
- No index was added: the meta-session lookup joins `approval.run_id` to `run` and expects small tables.

**Implementation notes (T3.4, Proposed, Delegated).** Code: `src/lifecycle/approval.ts` (decision rules, application,
bypass verdict), `src/cli/operator.ts` and `src/cli/runs.ts` (`approve`, `deny`), `src/reconcile/reconcile.ts`.

- `approve` and `deny` follow the `runs cancel` pattern ([ADR-0005](../adr/0005-sqlite-ledger.md), [TDD
  §3.5](TDD.md#35-concurrency-model)): after the checks in **Approve** above, the CLI appends an
  `operator_decision_requested` `run_event` (decision, approval ID, OS user, the scope hash it checked) in the same
  transaction. With no daemon (the CLI holds the data-directory lock) it applies the decision at once; otherwise `serve`
  applies it on its operator poll, or startup reconciliation does. Applying re-runs every check, then writes the row
  (`decided_at` is the time of the CLI's record, `decided_by` its OS user), an `approval_decided` event, the run's
  transition (T3 to QUEUED, or T19 to CANCELLED) and an `operator_decision_applied` event in one transaction, so the row
  and the run state change together; a decision that no longer applies gets `operator_decision_rejected` and changes
  nothing. While a decision or a cancel is pending for the run, a further `approve` or `deny` is refused.
- The **Approve** checks also require that the run's snapshot names this approval and carries the same `scopeHash`, and
  that the hash recomputed from the row's stored `scope_json` equals `scope_hash`; the **Bypass** check applies the same
  three hash comparisons and also requires the row to have been requested by a run of the same meta-session and client.
- The **Bypass** check runs in `RunLifecycle` at dispatch (PREFLIGHT, before any probe), not in `src/policy`; a mismatch
  is FRD T8 with `PERMISSION_BLOCKED`, and the transition event names the failed check (never a hash or scope content).
- `get_run include_events` drops `requested_by` and `scope_hash` from `operator_decision_requested` events.
- An approved run is QUEUED without the ingress queue bound (FRD T3 has no such guard).

## 4. Failure taxonomy

`failure_code` on a `FAILED` run holds exactly one of these codes. `ELIGIBILITY_NONE` and `INVALID_REQUEST` were **added
during planning** (not in [R2]'s list). Retryability follows FR-CAP-05: only `RATE_LIMIT_TRANSIENT`,
`PROVIDER_OVERLOADED` and `PROCESS_CRASH` before any workspace mutation retry automatically; rollback-or-resume instead
of replay follows FR-WS-04.

| Code | Meaning | Retryable? | Workspace action | Typical sources |
| --- | --- | --- | --- | --- |
| `AUTH_REQUIRED` | Provider not logged in; operator must log in natively | No | None (no mutation expected); report login command | `authPreflight`; headless auth error (FR-AUTH-02) |
| `PERMISSION_BLOCKED` | Operation denied by profile/permission rules, or caller above its max profile | No | Roll back if mutated | Provider permission-denied event; MCP caller check (FR-MCP-06, FR-POL-05) |
| `SANDBOX_VIOLATION` | Sandbox blocked an action | No | Roll back if mutated; flag for operator review | Provider sandbox event; outer sandbox denial (FR-POL-05) |
| `MODEL_UNAVAILABLE` | Requested model not present or not entitled | No (re-route may succeed) | None | Provider error category; model registry miss |
| `QUOTA_EXHAUSTED` | Subscription limit hit | No automatic retry; fail over, queue until known reset, or return (FR-CAP-06) | Roll back if mutated | Provider-reported limit; billing error category |
| `RATE_LIMIT_TRANSIENT` | Short-term throttle | Yes, if workspace unchanged | None if clean; else rollback or resume | Rate-limit error event; 429-like category |
| `PROVIDER_OVERLOADED` | Provider-side overload/server error | Yes, if workspace unchanged | As above | `overloaded`/server error categories |
| `TOOL_FAILURE` | Agent tool or command failed in a way the run cannot continue | No | Keep result if checkpointed, else roll back | Provider tool error; non-zero exit with error event |
| `TEST_FAILURE` | Verification commands failed after the agent finished | No | Keep post-run checkpoint (work product), mark failed verification | Verification stage (FR-EXE-08, M3) |
| `PROCESS_TIMEOUT` | Wall-clock or idle timeout; process group killed | No | Assess mutation; roll back or keep as unverified | Supervisor timers (FR-EXE-01) |
| `PROCESS_CRASH` | Provider process died abnormally, or controller restart orphaned it (cause `controller_restart`, FR-EXE-06) | Yes only if no mutation since pre-run checkpoint | Mutation check before any action | Signal/exit; reconciliation |
| `OUTPUT_PROTOCOL_ERROR` | Unparseable, oversize-line or unexpected-protocol output | No | Assess mutation; roll back if changed | Parser; line limit (§8) |
| `ADAPTER_VERSION_UNVERIFIED` | Installed version outside the validated range, or unknown or unparseable (a missing manifest is `ELIGIBILITY_NONE`, [FRD BR-3](../requirements/FRD.md#3-business-rules)) | No | None | Probe; manifest check (FR-ADP-03, FR-POL-07) |
| `CANCELLED` | Operator or caller cancelled | No | Roll back to pre-run checkpoint unless operator keeps partial work (Proposed) | `cancel_run`, WF-4 |
| `ELIGIBILITY_NONE` *(added during planning)* | No provider passes hard eligibility for this request | No (state may change) | None | Router (FR-RTE-01, FR-MCP-05) |
| `INVALID_REQUEST` *(added during planning)* | Schema, path, size or idempotency validation failed | No | None | MCP validation (FR-MCP-09, FR-POL-10) |

`CANCELLED` is also a run *state* (FRD); the code is used in error envelopes and `run_event` payloads, while a cancelled
run has `state = 'CANCELLED'` and `failure_code` NULL per the DDL check.

Inner-agent failures (unreachable, timeout, invalid output, open circuit, suspension) are **not** run failure codes: they
never fail a run, never appear in `run.failure_code` and never feed retry (FR-INN-06, FR-INN-08); they are recorded as
`inner_call` outcomes and `inner_*` run events ([§13.8](#138-telemetry-and-events)).

## 5. Workspace and lease algorithm

Implements FR-WS-01..06 and [ADR-0006](../adr/0006-worktree-checkpoints-no-blind-replay.md). All Git commands use
`execFile('git', args)` with a scrubbed environment, `-c core.hooksPath=/dev/null` and `--no-verify` on commits
(Proposed, see [TDD §3.4](TDD.md#34-security-engineering)); porcelain/`-z` output only.

**Naming.** Worktree path `<data_dir>/worktrees/<sess>/<run>`; branch `switchboard/<sess>/<run>`. One controller branch
per run, created from the previous head, so history per meta-session is a linear chain of run branches (Proposed).
`inspect-untrusted` on a non-Git directory uses no worktree and read-only access (FR-WS-06).

**Lease (one writer per meta-session chain, Proposed).** Because each run branches from the session head, two concurrent
writers would fork; the lease lives on `meta_session` (`lease_run_id`, `lease_expires_at`). Parallel tasks use separate
meta-sessions and therefore separate worktrees (FR-WS-02). Parallel subtasks inside one session: to be detailed in M5.

```mermaid
sequenceDiagram
  participant S as Scheduler
  participant L as Ledger txn
  participant W as Workspace Manager
  participant X as Supervisor
  S->>L: BEGIN IMMEDIATE; check lease free or expired; set lease_run_id, expires_at; run -> LEASED; event
  L-->>S: COMMIT
  S->>W: resolve base (session head); write 'pre' checkpoint row (intent)
  W->>W: git worktree add -b branch path base; record pre checkpoint
  S->>X: spawn (run -> RUNNING); heartbeat extends lease_expires_at
  X-->>S: exit + events
  S->>W: detect mutation, commit post checkpoint, write diff artifact
  S->>L: run -> FINALIZING/terminal; release lease; head_commit = post; event
```

**Acquire.** In one `BEGIN IMMEDIATE` transaction: if `lease_run_id IS NULL` or `lease_expires_at < now`, set both and
transition the run to `LEASED` with an event; otherwise the run stays queued. Lease TTL default 2 x wall-clock timeout,
extended by a heartbeat while the supervisor holds the process (proposed target; values in §8). An expired lease whose
holder run is non-terminal is resolved by reconciliation, not by simply stealing it: the stale run is first marked
`PROCESS_CRASH` (cause `lease_expired`) and its worktree assessed.

**Base and pre-run checkpoint.** Base = `meta_session.head_commit`, or for a new session the repository `HEAD` of the
allowed workspace (read via `git rev-parse`; the operator's checked-out branch and working tree are never modified,
FR-WS-05). A `base` row is written to `workspace_checkpoint`, then `git worktree add -b <branch> <path> <commit>`. The
`pre` checkpoint equals the base commit of the worktree; no commit is made at this point because the worktree starts
clean.

**Post-run checkpoint (FR-WS-03).** After the process exits and verification (if any) ends: `git add -A` in the worktree
(hooks disabled), `git commit` with a controller identity and the run ID in the message, record `post` checkpoint row,
write `diff` (`git diff --binary <pre>..<post>`) and `changed_files` artifacts. Commit is skipped if the tree is clean.

**Mutation detection.** Before any retry, rollback or resume decision, compare worktree to the `pre` commit: `git status
--porcelain=v2 -z --untracked-files=all` plus `git diff --quiet <pre>` and `HEAD == pre`. Any difference, a changed
`HEAD` or an unreadable worktree counts as *mutated* (fail closed, NFR-SEC-06). Known limits: ignored files are not
tracked by default (Proposed: also check with `--ignored` for the profile's high-risk patterns) and writes outside the
worktree are out of Git's sight; the sandbox, not detection, bounds those.

**Failure handling (FR-WS-04).** Unchanged worktree: eligible for retry per §9. Mutated: either `git reset --hard <pre>
&& git clean -fd` in the worktree (rollback; the failed attempt's diff is saved as an artifact first), or native resume
of the provider session on the same worktree, which counts as a continuation and never replays the original request.
Choice is policy-driven; default rollback for `TOOL_FAILURE`/`OUTPUT_PROTOCOL_ERROR`, resume only when the adapter
reports a resumable session (Proposed).

*As built in M1 (FRD §4.4 owns the outcome, so it wins over the destructive reset above):* the run lifecycle commits the
failed attempt's state to the run's own branch as an evidence checkpoint, stores the diff artifact, and moves the
meta-session head back to the pre-run checkpoint; it does not run `git reset --hard` / `git clean` on the evidence.
`WorkspaceManager.rollback` exists in `src/workspace/` but the lifecycle follows FRD §4.4. The reset-based wording above
is superseded for the lifecycle path.

**Push and operator tree.** The workspace manager never runs `git push`, touches no remote and writes nothing to the
operator's working tree or checked-out branch; the result is the run branch plus diff artifact (FR-WS-05). Publication
is a separate, policy-gated path owned by COMP-GIT ([§12](#12-injected-git-tools-commits-and-publication)). Checkpoint
commits here carry the controller identity and the run ID in their message, which is acceptable only because they are
internal: they are never pushed and never part of the publish ref (FR-GIT-08). *As built in M1* the checkpoints are
made on the run branch `switchboard/<sess>/<run>` with the identity in `src/workspace/git.ts`; M9 must not change
that, only add the publish ref beside it.

**GC (FR-WS-07, NFR-DATA-01, M3; to be detailed in M3).** Retention job deletes, per expired terminal run, in one
logical unit: worktree directory (`git worktree remove --force`, then `git worktree prune`), controller branch,
artifact files (set `deleted_at`). Never touches branches outside `switchboard/`. From M9 the publish refs (§12.3) are
collected with the rest of their meta-session. Orphan sweep: worktree directories or `switchboard/*` branches with no
matching `run` row are reported by `doctor` and removed only by GC after the retention period.

*As built (T3.12, Delegated decision 28 under owner decision 25):* the unit is a whole idle meta-session
([Q-18](../ROADMAP.md#73-open-questions-for-zemdregon-not-blocking-m2-unless-noted), `src/workspace/gc.ts`; `run_event`
rows are kept, Q-19). It is wired three ways, none with a new config key. `doctor` reports what `retention.days`
(default 30) would collect and the orphan sweep, read-only (`findOrphans`, `planRetentionGc`). `switchboard gc` lists
the same by default (dry run); `--apply` collects, needs `retention.days` set in the config and the data-directory
lock (so it is refused while `serve` runs). `serve` runs one pass after reconciliation, before the lifecycle starts or
MCP accepts calls, and then every `retention.interval`, only when `retention.days` is set: unset means nothing is
collected. Orphans are reported but not yet removed. GC marks first (R-42, decision 28): one transaction re-checks idleness,
sets the meta-session `ARCHIVED` and appends the intent event, and admission refuses an `ARCHIVED` meta-session with
`INVALID_REQUEST`; a marked, unfinished session is a candidate again and rolls forward.

**Crash safety.** Order is intent row (with the `ARCHIVED` mark, one transaction), then Git action, then outcome
row. On startup reconciliation (WF-8) a run in
`LEASED`/`RUNNING` with a worktree but no outcome is assessed by the mutation check; a lease row is cleared only after
its run reaches a terminal state. `git worktree add` interrupted mid-way is detected by `git worktree list` disagreement
and repaired by remove-and-recreate before the pre-state is used.

**Eligibility effect (FR-POL-07, FR-ADP-03).** The adapter is ineligible if: no manifest exists (failure code

## 8. Run supervisor details

`COMP-EXE` implements FR-EXE-01..07 for the `subprocess-jsonl` transport (M1); `acp-stdio` is to be detailed in M4;
`local-service` deferred (FR-EXE-04).

- **Spawn.** `spawn(argv[0], argv.slice(1), { cwd, env, detached: true, stdio: ['pipe' or 'ignore', 'pipe', 'pipe'],
  shell: false })`. `detached` puts the child in a new session and process group (`pgid = pid`). Persist `pid`, `pgid`
  and process start ticks (from `/proc/<pid>/stat` on Linux) in `run` *before* reading any output, so reconciliation can
  tell a live orphan from a reused PID.
- **Stdin.** Closed (`ignore`) unless the Invocation supplies stdin text; prompts passed on stdin rather than argv where
  an adapter supports it, to keep them out of process listings (to be verified per adapter).
- **Cancel and timeout.** On cancel, wall-clock or idle timeout: send `SIGTERM` to `-pgid`, wait `killGraceMs` (10 s,
  proposed target), then `SIGKILL` to `-pgid`; confirm group empty (`kill(-pgid, 0)` fails with ESRCH) before reporting
  terminal. Defaults (proposed targets): wall-clock 30 min, idle (no stdout bytes) 5 min, preflight probe 30 s; all
  configurable. Timeout yields `PROCESS_TIMEOUT`, cancel yields `CANCELLED`.
- **Line framing.** Stdout is decoded as UTF-8 and split on `\n` (tolerating `\r\n`); one JSON document per line for
  JSONL transports; for `json` output, the entire stdout is one document capped at the artifact limit. Max line size 1
  MiB (proposed target): an oversize line aborts the run as `OUTPUT_PROTOCOL_ERROR` (kill group, keep captured data),
  never truncated silently. Invalid UTF-8 or JSON on a line is a protocol error unless the adapter declares the line
  type ignorable.
- **Capture.** Raw stdout and stderr are streamed to files in a temp area as received, then moved into the artifact
  store and hashed on completion (`provider_stdout`, `provider_stderr`, FR-EXE-05); stderr is never parsed as protocol.
  Per-stream size cap 64 MiB (proposed target); beyond it capture stops, a `run_event` records truncation, and the run
  continues.
- **Backpressure.** Events are parsed and enqueued to an in-memory bounded buffer (1,000 events, proposed target)
  drained by a single ledger writer that batches inserts per transaction. When the buffer is full the supervisor
  `pause()`s the child's stdout stream so the OS pipe fills and the provider blocks; it resumes at half capacity.
  High-rate partial-delta events are coalesced and not stored individually (Proposed); the raw stream remains in the
  artifact.
- **Exit.** On `exit` + stream `close`, collect `{code, signal}`, flush the writer, then call `extractResult` and
  `classifyFailure`. A controller-side exception in one run's task is contained and fails only that run (NFR-REL-02).
- **Environment.** Built per Invocation from the allowlist (FR-EXE-07); the supervisor asserts no key outside
  `envAllowlist` is present.
- **Reconciliation (WF-8).** For each non-terminal run on startup: if `pgid` is set and a process matching
  `proc_start_ticks` exists, send the cancel sequence to its group (the controller cannot re-attach to its pipes); then
  run the mutation check (§5) and mark `PROCESS_CRASH` with cause `controller_restart` (FR-EXE-06). Killing a still-live
  orphan is a **Proposed** extension of FR-EXE-06, which speaks only of dead processes.
  *As built in M1 (Proposed, Linux `/proc` based, `src/reconcile/process.ts`):* a live orphan group is terminated when
  its leader's start ticks equal the recorded ticks, or when the leader is gone but the group still has live members
  (Linux does not reuse a PID still in use as a group ID). A leader with different ticks (PID reuse) or with no recorded
  ticks is never signalled. Known limit: a crash between spawn and the `pid`/`pgid` commit leaves an orphan that cannot
  be found (ROADMAP R-12).

## 9. Retry/back-off algorithm

Applies only to `RATE_LIMIT_TRANSIENT`, `PROVIDER_OVERLOADED` and pre-mutation `PROCESS_CRASH`, and only when the
mutation check shows the worktree equals the pre-run checkpoint (FR-CAP-05). Full jitter with a cap; parameters are
proposed targets until M6 measurement:

```text
delay(n) = random_uniform(0, min(cap, base * 2^(n-1)))     n = attempt number of the failed run, starting 1
base = 2 s   cap = 120 s   max_attempts = 3  (initial try + 2 retries)
if provider reported a reset or retry-after time: delay = max(delay, reported - now), bounded by the queue horizon
```

Procedure: failure classified; mutation check; if clean and attempts remain, insert a new `run` (`attempt+1`,
`parent_run_id` set, same `request_hash`, fresh worktree from the same base) in `WAITING_CAPACITY` or `QUEUED` with
`next_attempt_at`; the scheduler wakes on `next_attempt_at` (persisted, so it survives restart). A retry re-runs
preflight and routing, so a breaker or ineligibility ends the retry chain. Dirty workspace: no retry, FR-WS-04 applies.
`QUOTA_EXHAUSTED` follows FR-CAP-06 (failover, else queue if a reset is known within `capacity.queue_horizon`, else
return); no backoff makes a hard quota disappear. Breakers, adaptive concurrency and failover details: to be detailed in
M6.

## 10. Idempotency and ordering

- **Write before side effect.** Every externally visible action is preceded by a committed ledger row recording intent:
  the `run` row (`QUEUED`) before returning from `delegate_task`; `LEASED` and the lease before `git worktree add`;
  `pid`/`pgid` before reading output; `FINALIZING` before the post-run commit. A crash between intent and effect is
  repaired by reconciliation, which re-derives truth from Git and the process table.
- **State transitions** (states and edges owned by [FRD](../requirements/FRD.md); not redefined here) are single SQL
  transactions:

  ```sql
  BEGIN IMMEDIATE;
  UPDATE run SET state=:to, version=version+1, updated_at=:now /* + failure_code, finished_at ... */
    WHERE id=:id AND version=:expected AND state=:from;     -- changes() must be 1, else ROLLBACK
  INSERT INTO run_event (id, run_id, seq, ts, type, payload_json)
    VALUES (:evt, :id, (SELECT COALESCE(MAX(seq),0)+1 FROM run_event WHERE run_id=:id), :now, 'state_transition', :p);
  COMMIT;
  ```

  Transition and event always commit together (ADR-0005). A failed `changes()` check means another actor moved the run
  (for example cancel vs. completion); the loser re-reads and re-decides. Terminal states are never left.
- **Event sequence numbers.** `seq` is per run, gapless from 1, assigned inside the writing transaction; `UNIQUE(run_id,
  seq)` is the backstop. Only the controller's single writer allocates sequences, so there is no cross-process race (TDD
  §3.5). Consumers (`get_run include_events`, `runs show`) page by `after_seq`.
- **Idempotent API calls.** `(client_id, idempotency_key)` is unique; the stored `request_hash` (SHA-256 over canonical
  JSON of the validated input) distinguishes replay from conflict (FR-MCP-08). The check and the insert happen in the
  same transaction. Calls without a key are not deduplicated.
- **Idempotent reconciliation.** Reconciliation (WF-8) can be re-run safely: each step is conditional on the current
  state and writes an event once.
- **Retention and migrations** interact with ordering only through `schema_migrations`; migrations run before any run
  processing starts (TDD §6).

## 11. Projects, contexts and environments

Implements FR-PRJ-01..10 and [ADR-0013](../adr/0013-projects-environments-and-contexts.md). **Proposed** shapes; M9
(`host`) and M10 (`container`).

### 11.1 Configuration shape

Part of the config schema ([TDD §3.1](TDD.md#31-configuration)); validated with Ajv at startup; an unknown key or
context kind aborts startup (NFR-SEC-06).

```jsonc
{ "projects": [ {
    "id": "web-app",                                   // ^[a-z][a-z0-9-]{1,40}$
    "name": "Web application",
    "environment": { "kind": "host" },                 // or { "kind": "container", "image_digest": "sha256:...", "limits": { "cpus": 2, "memory_mb": 4096, "disk_mb": 8192 } }
    "max_trust_profile": "edit-untrusted",             // optional; lowers the ceiling (FR-PRJ-06)
    "allowed_providers": ["claude", "codex"],          // optional
    "contexts": [ {
        "id": "main", "kind": "repository",            // only kind in this design; others fail validation
        "path": "/home/op/src/web-app",                // canonicalized, under allowed_roots (FR-POL-10)
        "base_ref": "main",
        "primary": true,                               // exactly one primary context; its worktree is the agent's cwd
        "writable": true,                              // non-primary contexts are read-only mounts (Proposed)
        "push": { "policy": "none" },                  // or { "policy": "branch", "remote": "origin", "branch_prefix": "switchboard/" }
        "identity": { "name": "Operator Name", "email": "operator@example.com" },
        "sign": false                                  // true: controller signs published commits (FR-GIT-10, §12.3.1)
    } ] } ],
  "mcp_clients": [ { "id": "openclaw", "max_trust_profile": "edit-untrusted", "projects": ["web-app"],
                     "manage_projects": false,           // default; true offers create/update/delete_project (FR-PRJ-10)
                     "max_push_policy": "none" } ] }     // widest push policy a dynamic project of this client may use
```

Only the primary context is writable in this design; additional writable contexts (multi-repository changes) are deferred
(ROADMAP §8). A context with `push.policy` other than `none` must have an `identity`.

*Note (2026-10-13, Delegated, [decision 29](../ROADMAP.md#42-owner-decisions), T3.21):* the top-level `timeouts` object
is part of the same Ajv-validated schema (strict; unknown keys abort startup) and today holds one key,
`"timeouts": { "preflight_ttl_seconds": 60 }` (integer 0 to 3600; default 60 is an **Assumption**; 0 disables the
preflight cache, NFR-PERF-02). The cache holds only successful `probe` and `OK` auth results, keyed by adapter id and
the resolved binary's path, `mtime`, size and inode, so an upgraded binary is re-probed immediately and a failure or
an unauthenticated state is re-checked on the next call (used by `delegate_task`, dispatch and `list_capabilities`; [§2](#2-adapter-contract)).

*As built (2026-10-13, Delegated, T9.1):* `projects[]` is in the Ajv schema (`src/config/schema.ts`, strict: unknown keys
and context kinds abort startup with the JSON path) and `loadConfig` adds the structural rules: unique project and
context ids, exactly one primary context (a sole context is primary unless it says `"primary": false`), only the
primary context writable (default: writable iff primary), `push.policy: "branch"` needs `remote` and `branch_prefix`
(**Assumption**, from the example above), any push other than `none` needs `identity`, `image_digest` required for
`container` and refused for `host`. `base_ref` is required (FR-PRJ-02). Context ids match `^[a-z][a-z0-9-]{0,40}$` and
the image digest `^sha256:[0-9a-f]{64}$` (**Assumptions**). `allowed_providers` takes the provider IDs of
`PROVIDER_IDS` (`claude-code`, `codex`, ...), not the short `claude` shown in the example. `max_trust_profile`,
`allowed_providers` and `sign` are checked for shape only; enforcement is T9.2 and T9.10. The filesystem rules run only
in `switchboard projects validate` (absolute path; `realpath` under an allowed root, so `..` and symlink escapes are
refused; a Git repository whose top level is also under an allowed root; `base_ref` resolves to a commit; a `container`
environment fails with "container environments are not implemented yet (M10)"), so `serve` starts on a config that
lists projects exactly as before and never starts a container. `mcp_clients[].projects`, `manage_projects` and
`max_push_policy` are not in the schema yet (T9.2, T9.9).

### 11.2 Resolution and ceilings

At admission (FRD BR-23): (1) resolve `project` to its definition, else `INVALID_REQUEST`; (2) check the client's project
list, else `PERMISSION_BLOCKED`; (3) effective ceiling = the lower of the client's and the project's `max_trust_profile`
on the order `inspect-untrusted` < `edit-untrusted` < `test-sandboxed` < `trusted-development` < `privileged`, and a
request above it is `PERMISSION_BLOCKED`; (4) remove providers outside `allowed_providers` from the candidate set;
(5) canonicalize the primary context's path against the allowed roots again (config may have changed); (5a) for a
dynamic project use the highest `ACTIVE` revision with `approved_at` set where approval was required, else
`PERMISSION_BLOCKED` with `approval_required`; (6) freeze the
resolved project, environment (kind, image digest, limits), push policy and identity into `policy_snapshot_json`.

A project created by an orchestrator uses the same shape and is validated by the same code. Its `identity` must be copied
from a configured value the operator named in the client entry (`identities` list), so an orchestrator cannot invent an
author (Proposed); the repository `path` must already exist under an allowed root. Approval is `projects approve <id>
[--revision n]`, an operator CLI command that writes `approved_at`; it has no MCP counterpart (FRD BR-32).

### 11.3 Environment port

COMP-EXE reaches the provider process through one port, so `host` and `container` share the supervisor logic:

```ts
export interface Environment {
  readonly kind: 'host' | 'container';
  /** host: returns the invocation unchanged. container: wraps it so the process runs inside the container. */
  prepare(run: RunContext, invocation: Invocation): Promise<PreparedInvocation>;   // creates the container (M10)
  /** Always called, on every terminal path; idempotent. */
  teardown(run: RunContext): Promise<void>;
  /** Startup reconciliation: containers carrying switchboard labels with no matching live run (FR-PRJ-07). */
  sweepOrphans(knownRunIds: ReadonlySet<string>): Promise<{ removed: string[] }>;
}
```

`host` is the identity implementation and keeps today's behaviour. A `container` implementation must not mount more than
FR-PRJ-05 allows, refuse an image with a Git client (`git` or `gh` on the container's `PATH`, FR-PRJ-05), label every
container `switchboard.run` and `switchboard.project`, and record `environment` run events. All Git operations for a
container run stay in the controller on the host.
Container details: [TDD §3.11](TDD.md#311-container-environments).

## 12. Injected Git tools, commits and publication

Implements FR-GIT-01..09 and [ADR-0014](../adr/0014-tool-only-commits-and-publication.md). **Proposed** mechanisms; zemdregon
decided that agents have no commit or push ability and that tools injected by Switchboard do both. Layers and
per-provider unknowns: [TDD §3.10](TDD.md#310-git-commits-attribution-and-publication).

### 12.1 Tool contracts

Served by the shim to the agent as MCP tools; every object has `additionalProperties: false`.

```jsonc
// commit  (always offered under write-capable profiles when the adapter's commitChannel is "injected")
// M11: "message" is required only unless the commit_message task is enabled with mode != never (see below)
{ "input": { "type": "object", "required": ["message"], "properties": {
    "message": { "type": "string", "minLength": 1, "maxLength": 8192 },
    "paths":   { "type": "array", "items": { "type": "string" }, "maxItems": 256 } } },     // worktree-relative; default: all changes
  "output": { "sha": "string", "files_changed": "integer" } }

// push  (offered only when the context policy is "branch" and BR-31 holds)
{ "input": { "type": "object", "properties": {} },        // no arguments: the ref, remote and prefix come from configuration
  "output": { "pushed": "boolean", "ref": "string", "head_sha": "string" } }
```

`push` takes no arguments on purpose, so an injected agent cannot choose a ref. Tool errors use short codes
(`NOT_RUNNING`, `LEASE_LOST`, `PATH_OUTSIDE_WORKTREE`, `NOTHING_TO_COMMIT`, `MESSAGE_EMPTY_AFTER_SANITISING`,
`PUSH_NOT_ALLOWED`, `CREDENTIALS_UNAVAILABLE`, `REMOTE_REJECTED`, `SIGNING_FAILED`, and, from M11, `MESSAGE_REQUIRED`)
and are `git_tool_denied` or `git_push` events. They are returned to the agent and do not fail the run.

**`message` and the inner agent (M11, FR-INN-10, Proposed).** `message` stays required in the published tool schema
unless the `commit_message` task is enabled with `mode` other than `never`; the shim then serves the schema with no
required field, generated per run from the effective configuration. With `draft_if_missing` the agent's own message
always wins and no inner call is made when it is present and non-empty; with `always` the draft is requested even when
the agent supplied one. `MESSAGE_REQUIRED` is returned when no message was supplied and the draft is unavailable
(disabled, suspended, denied by a privacy gate, timed out, circuit open), empty, invalid, or empty after sanitising; its
text asks the agent to call `commit` again with a `message`. The controller never writes a stand-in message. Under
`always`, an unusable draft falls back to the agent's message when there is one, and returns `MESSAGE_REQUIRED` when not.
`MESSAGE_EMPTY_AFTER_SANITISING` keeps its meaning for a message the agent supplied. The tool call waits for the inner
call at most the per-call bound ([§13.4](#134-call-pipeline)).

### 12.2 Channel

The controller creates `<data_dir>/runs/<run_id>/tools.sock` (directory mode `0700`, socket `0600`) and a random per-run
capability token before spawn, and writes the provider-form MCP definition from `channelArgs`: a command that starts
`switchboard tool-shim --socket <path>` with the token in the shim's environment. The shim speaks MCP on stdio to the agent
and newline-delimited JSON to the controller. The controller accepts only connections presenting the token for a run that
is RUNNING, and closes and removes the socket when the run leaves RUNNING. Nothing the agent sends is trusted beyond the
validation in §12.3. Whether provider sandboxes permit the connect is verified per adapter; if not, that adapter is
`finalize-only`.

*Note 2026-10-13 (T9.0 spike; Delegated; findings only, owner text above unchanged).* For Claude Code the per-run
definition is `--mcp-config <json file or string>` with `--strict-mcp-config` (`claude --help` 2.1.296); the JSON shape,
the MCP tool's allow-rule form and whether `--safe-mode` also disables it are unverified, and `--mcp-config` is barred
by ADR-0015 and the argv audit until a new ADR narrows that bar (ROADMAP Q-40). Codex: unverified (no installed binary,
not in [R2]). Whether either provider's sandbox lets the shim connect: `Unknown: live check`. A UNIX socket path is
limited to 108 bytes by the kernel (`/usr/include/linux/un.h`); `<data_dir>/runs/<run_id>/tools.sock` can exceed that
under a long data directory, so the controller should check the length when it creates the socket (Python `bind` failed
at 167 bytes and `gpg-agent` failed to start under a long path on this host; Node 22.22.0 accepted 157 bytes, behaviour
not investigated). Details and sources: [TDD §3.10](TDD.md#310-git-commits-attribution-and-publication).

### 12.3 Commit algorithm and refs

Refs (Proposed): the **publish ref** for a meta-session is `refs/heads/<prefix><sess>`, where `<prefix>` is the context's
`push.branch_prefix` (default `switchboard/pub/`), kept apart from the internal run branches `switchboard/<sess>/<run>`.

1. Verify the run is RUNNING and holds the lease; the path set is inside the worktree after canonicalization.
2. Build a temporary index file seeded from the publish ref's tree (or the run's base commit for the first commit); add
   the requested paths, or all worktree changes, from the worktree; write the tree. If the tree equals the parent's,
   `NOTHING_TO_COMMIT`.
   *(M11)* If the `commit_message` task applies (no agent message, or `mode` `always`), the inner pipeline
   ([§13.4](#134-call-pipeline)) runs here on the diff between the parent tree and the new tree, limited to the paths
   being committed. The result is a draft message or "unavailable".
3. Sanitise the message (§12.4); drafted text goes through exactly the same sanitiser, with the same built-in and
   operator patterns, as the agent's own text. If it is empty afterwards, `MESSAGE_EMPTY_AFTER_SANITISING` for an agent
   message and `MESSAGE_REQUIRED` for a draft or when neither exists.
4. Create the commit object with author and committer set to the context identity, current time, no trailers, no
   signature unless the context sets `sign: true` (§12.3.1), hooks disabled and a scrubbed environment (as in §5).
5. Move the publish ref from the old head to the new commit with a compare-and-swap; on a lost race, retry from step 2
   once, then fail the call.
6. In one ledger transaction insert the `git_commit` row and the `git_commit` run event.

**Note 2026-10-13 (T9.0 spike; Delegated; verified on Git 2.43.0 in a throwaway repository with a neutral configuration;
owner text above unchanged).** The plumbing below built a commit from a path subset, with the worktree's own index file,
`HEAD` and run branch byte-for-byte unchanged (`sha256sum` of the worktree index before and after was identical; `git
status --porcelain` identical; `HEAD` and the run branch unchanged). The lab ran with `GIT_CONFIG_GLOBAL` set to an
empty file and `GIT_CONFIG_SYSTEM=/dev/null`, not through `src/workspace/git.ts`; the controller adds `scrubbedGitEnv()`
and `-c core.hooksPath=/dev/null` (see Hooks below). `cwd` was the worktree and `GIT_INDEX_FILE` an absolute path
outside the worktree and its Git directory.

| Step | Command | Observed on 2.43.0 |
| --- | --- | --- |
| Seed | `GIT_INDEX_FILE=$IDX git read-tree <publish head or base>` | temporary index holds the parent's tree |
| Add | `GIT_INDEX_FILE=$IDX git --literal-pathspecs add -- <path>...` (or `--pathspec-from-file=- --pathspec-file-nul` with NUL-separated paths on stdin) | adds modified and new files and **stages deletions** (a deleted `sub/s.txt` left the tree); other changed files stay out of the tree |
| Tree | `GIT_INDEX_FILE=$IDX git write-tree` | tree id; equal to the parent's `^{tree}` means `NOTHING_TO_COMMIT` (checked with a second identical add) |
| Commit | `printf '%s' "$msg" \| GIT_AUTHOR_NAME=.. GIT_AUTHOR_EMAIL=.. GIT_AUTHOR_DATE=.. GIT_COMMITTER_NAME=.. GIT_COMMITTER_EMAIL=.. GIT_COMMITTER_DATE=.. git commit-tree <tree> -p <parent> -F -` | commit object with exactly the author, committer and dates given (`2026-10-13T10:00:00Z` gave `1791885600 +0000`), the message and no trailer |
| Publish | `git update-ref refs/heads/<publish> <new> <old>`; `<old>` is 40 zeros for the first commit | succeeds with the right old value; with 40 zeros on an existing ref: `cannot lock ref ...: reference already exists`; with a wrong old value: `is at <sha> but expected <sha>` (rc 128 each), which is the compare-and-swap of step 5 |

Observations the algorithm should respect:

- **Pathspecs.** Without `--literal-pathspecs`, `git add -- '*.txt'` staged every matching file; with it, the same
  argument matched nothing (`fatal: pathspec '*.txt' did not match any files`). A path that is literally `we*ird[1].txt`
  staged only that file in both modes when named exactly (exact names win), so use the literal flag for safety, not
  because exact names break. `git add -- ../outside.txt` is refused (`fatal: ... is outside repository`, rc 128);
  a missing path is refused (`did not match any files`, rc 128); an ignored path is refused (`The following paths are
  ignored by one of your .gitignore files`, rc 1) and `git add -- .` skips it. The commit tool's own
  `PATH_OUTSIDE_WORKTREE` check still comes first.
- **Checkpoints stay out of the publish history.** After a checkpoint commit was made on the run branch with the same
  temporary-index method (author `Switchboard <switchboard@localhost>`), `git rev-list refs/heads/<publish>` listed only
  the publish commits and the base, `git merge-base --is-ancestor <checkpoint> <publish>` returned 1, and
  `git for-each-ref --contains <checkpoint> refs/heads/switchboard/pub/` printed nothing. This holds by construction:
  each publish commit's parent is the previous publish commit or the base, never a run-branch commit.
- **Second commit** seeded from `read-tree <publish ref>`, then `add -- c.txt`, gave a tree whose
  `git diff-tree -r <first> <second>` was exactly `A c.txt`.
- **Reflog.** `update-ref` without `-m` records an empty reflog message; with `-m 'x'` it records `x`. The reflog stays
  local, but use no `-m`, or a fixed neutral text, so no identifier lands there.
- **Hooks.** Only `update-ref` was seen to run a hook (`reference-transaction`): with the layer 3 guard of [TDD
  §3.10](TDD.md#310-git-commits-attribution-and-publication) in the environment the update was refused, and with `-c
  core.hooksPath=/dev/null` or an environment without the guard it succeeded. The controller therefore must not inherit
  the guard variables. Whether `read-tree`, `write-tree` and `commit-tree` run any hook was not tested (none was configured
  for them in the lab).
- **Identity.** `commit-tree` takes identity from the four `GIT_AUTHOR_*`/`GIT_COMMITTER_*` variables; set all of them
  (and the dates) rather than relying on configuration, because Git may derive an identity from the host name.
- **Minimum versions.** Every command above exists on 2.43.0. Introduction versions are unverified, except
  `--pathspec-from-file`, which the Git 2.25.0 release notes introduce for "a few commands" without naming `git add`,
  so its availability for `add` below 2.43 is unverified. The decision on `MIN_GIT_VERSION` (raised to 2.32, ADR-0023) is
  in TDD §3.10 and ROADMAP Q-39.
- **Not tested.** Clean and smudge filters during `git add` (the controller already neutralises driver keys, TDD §3.4),
  nested repositories (ADR-0022), submodules, symlinks, very large path sets, concurrent publishers beyond the
  compare-and-swap above, and `-c core.hooksPath=/dev/null` under a Git older than 2.43.

#### 12.3.1 Signing (FR-GIT-10, Proposed)

With `sign: true` step 4 asks Git to sign the commit object using the operator's existing signing configuration
(`user.signingkey`, `gpg.format`, and the operator's own agent or keyring), run by the controller process with the
operator's environment, not the scrubbed one. The controller never reads, stores or logs the key, and never exports the
agent socket or `SSH_AUTH_SOCK`/`GPG_*` variables to the provider process (FR-EXE-07). Failure (no key, locked agent,
non-zero exit) returns `SIGNING_FAILED` to the agent and writes no commit. The BR-31 reach check applies: a context that
signs needs an environment in which the agent cannot reach the key. Which signing formats work in a headless controller
is verified in the M9 spike (T9.0); until then `sign` is accepted only if `projects validate` can produce a test
signature in a scratch repository.

**Note 2026-10-13 (T9.0 spike; Delegated).** Verified on Git 2.43.0 with GnuPG: `git -c user.signingkey=<fpr>
commit-tree <tree> -p <parent> -S -m signed` produced a commit with a `gpgsig` header and `git verify-commit` reported a
good signature, using a throwaway unprotected Ed25519 key generated in a temporary `GNUPGHOME` (no real key was used).
With `-c gpg.program=/nonexistent/gpg` the call exited 1 with `error: gpg failed to sign the data` and printed no commit
id, so a signing failure yields no commit, as `SIGNING_FAILED` requires. `gpg-agent` did not start with a `GNUPGHOME`
path longer than the socket limit (see §12.2). **Unverified:** SSH-format signing (`ssh-keygen` is not installed on this
host; the Git 2.34.0 release notes introduce it and warn against OpenSSH 8.7), X.509, passphrase-protected or hardware
keys, and signing with the operator's real agent. Only the unprotected-key GnuPG case counts as headless-verified.

The exact Git plumbing is fixed in the M9 spike. Nothing here touches the run branch, the worktree's index or the
operator's checkout.

### 12.4 Message sanitisation

Line-oriented. The built-in rules are illustrative starting points and **must be tested against fixtures** of typical agent
output before M9 is Done; operator patterns are added through `git.sanitize_patterns` (JavaScript regular-expression
sources, case-insensitive, validated at config load with a length limit; Proposed).

| Rule ID | Removes | Basis |
| --- | --- | --- |
| `trailer.co-author` | Any line starting `Co-authored-by:` | zemdregon's decision: no co-author trailers |
| `trailer.generated` | Lines starting `Generated-by:`, `Assisted-by:`, `Generated-with:` or `Assisted-with:` | Same; key list Proposed |
| `footer.generated-by` | Lines of the form "generated with/by ..." that name an AI tool, assistant or a provider or product from this project's provider list or Switchboard | Same |
| `id.controller` | Any token matching the controller's own ID formats (`sess_` or `run_` plus 26 ULID characters, [§3.0](#30-shared-types)) | Session IDs must not leak |
| `id.native-session` | The run's own provider-native session ID, as read from structured output (FR-ADP-04), wherever it appears | Same; exact-match, so no guessing |
| `url.session` | URLs whose path or query contains a session or conversation identifier of this run | Same |

After removal, runs of blank lines collapse and leading and trailing blank lines are trimmed. The controller never
adds a line. This holds for text drafted by the inner agent and for the PR draft ([§13.6](#136-task-contracts)): they
pass the same rules, with no inner-specific exceptions and no inner influence on the rule set (FR-INN-06). The removed
text is **not** recorded: `sanitizer_json` holds only `{ "rules": { "<rule id>": <count> }
}`. The rule set cannot catch what it does not describe, and it does not touch file contents (risk R-14).

### 12.5 Ref snapshot and violation handling

At LEASED the controller records `git for-each-ref` for the whole repository (all branches, tags and other refs, bounded
in size) as a hash plus the list of ref names and SHAs in a `run_event` payload. At FINALIZING it repeats the listing and
compares: expected differences are the run branch and the publish ref moved by the controller. For the run branch it also
checks that every commit between the base and the head was made by the controller. Any other difference, or a foreign
commit on the run branch, appends `git_policy_violation` (names of refs and SHAs, never messages), the foreign commits are
not reachable from the publish ref, and the tree content is kept as the working-tree changes the post-run checkpoint
records (FRD BR-27). The comparison reads the whole repository, so it also covers writes made through the main
repository's Git directory.

### 12.6 Push algorithm

1. Policy `branch`; the BR-31 credential-reach rule holds; the run (or, for an operator command, the meta-session) has a
   publish ref with at least one commit.
2. Compute the refspec from configuration: the publish ref to `<branch_prefix><sess>` on the configured remote. Refuse if
   the target equals the repository default branch or the checked-out branch, is a tag, or would not be a fast-forward
   (never force).
3. Run `git push` from the controller process with that explicit refspec, hooks disabled, using the operator's existing
   Git configuration for the remote. Capture the outcome; redact the output (no URLs with userinfo).
4. In one transaction insert the `git_push` row and event, and mark the pushed `git_commit` rows by recording the remote
   and ref in the event payload (the table itself stays append-only).

### 12.7 Provenance and audit

`git_commit` rows are the audit trail (FR-GIT-07). `runs show <id>` joins them to the run's provider, model and adapter
version and prints each commit's SHA, origin (`commit_tool` or `finalize_only`), push state and sanitiser counts.
Re-linking after an operator rewrite: match first on `commit_sha`, then `tree_sha`, then `patch_id` (best effort; Git's
`patch-id` command; to be verified against the pinned Git version). Records are never edited and the commit objects are
never annotated (notes were rejected, ADR-0014).

**Inner-agent provenance (M11, Proposed).** `git_commit` gains `message_source` (`agent` or `inner`, default `agent`) and
`inner_call_id` (the `inner_call` row of the accepted draft; NULL for an agent message). `runs show` prints both. The
message itself is never annotated or stored; the PR draft's provenance is its `pr_draft` artifact ID on the `inner_call`
run event.

## 13. Inner agent

Implements FR-INN-01..17 and [ADR-0016](../adr/0016-inner-agent.md) for M11 (COMP-INN, trust boundary TB-10). Task
catalogue and recommendations: [PRD §3.1](../requirements/PRD.md#31-inner-agent-task-catalogue). Everything here is
**Proposed** unless an SRS ID fixes it; no model name, port or provider flag is stated as fact, and every number is a
*(proposed target)*. An inner call is a stateless single-turn text completion with no tools (FR-INN-02). No inner output
is an input to COMP-POL, profile compilation, eligibility, approvals, ceilings, push policy, the sanitiser's rules,
redaction, failure classification or any run status (FR-INN-06); structure and the import-boundary test
([TDD §3.12](TDD.md#312-inner-agent)) enforce it, not prompting.

### 13.1 Configuration shape

Part of the config schema ([TDD §3.1](TDD.md#31-configuration)). With no `inner_agent` section, or `enabled: false`, every
task uses its fallback and nothing else changes (FR-INN-01). There is no default backend, model or task.

```jsonc
{ "inner_agent": {
    "enabled": true,                                   // master switch; default false
    "backend": {
      "kind": "http",                                  // or "cli" (FR-INN-04; Ineligible until verified, §13.2)
      "base_url": "http://127.0.0.1:<port>",           // http only; no userinfo, no query; or a Unix socket path form (§13.2)
      "model": "<model>",                              // operator-chosen placeholder; never defaulted
      "timeout_ms": 15000,                             // hard bound per task call, both attempts together (proposed target)
      "max_concurrency": 2,                            // per-backend semaphore (proposed target)
      "allow_remote": false,                           // true is required to use a backend classified remote (FR-INN-16)
      "shares_subscription_with": null                 // optional provider id; see FR-INN-15
      // cli kind instead of base_url: "provider": "opencode"   (flags and argv are adapter-owned, not configurable here)
    },
    "tasks": {
      "commit_message":   { "enabled": true,  "mode": "draft_if_missing",   // draft_if_missing | always | never
                            "allow_source_content": false, "input_budget_bytes": 24000, "max_output_tokens": 400 },
      "pr_draft":         { "enabled": false, "allow_source_content": false, "input_budget_bytes": 48000, "max_output_tokens": 1200 },
      "route_features":   { "enabled": false, "input_budget_bytes": 8000, "max_output_tokens": 100, "timeout_ms": 5000 },
      "handoff_condense": { "enabled": false, "allow_source_content": false, "input_budget_bytes": 32000, "max_output_tokens": 800 },
      "log_summary":      { "enabled": false, "allow_source_content": false, "input_budget_bytes": 32000, "max_output_tokens": 400 },
      "run_title":        { "enabled": false, "input_budget_bytes": 2000, "max_output_tokens": 80 }
    },
    "breaker":    { "failure_threshold": 3, "open_ms": 60000 },                          // proposed targets
    "suspension": { "window_calls": 50, "min_calls": 20, "rejection_threshold": 0.4 }    // proposed targets (FR-INN-09)
  } }
```

Rules (Ajv at startup; an unknown key or type error aborts startup, NFR-SEC-06):

- **No credential fields.** There is no key, token, header, password or environment-variable field. `base_url` is
  rejected if it carries userinfo or a query string; a value that looks like a credential is rejected at load (T11.1). A
  keyed hosted service is reached through an operator-run local gateway that holds the key, or through the `cli` kind,
  which keeps its own login (FR-INN-03, ADR-0003).
- `mode` is valid only on `commit_message`. `allow_source_content` is valid only on tasks that send repository content
  (`commit_message`, `pr_draft`, `handoff_condense`, `log_summary`; §13.5) and defaults to `false`. A task `timeout_ms`
  may only be lower than the backend's. `input_budget_bytes` has a floor of 1024 so the fixed header always fits.
- `shares_subscription_with` must name a configured provider id or be `null` (FR-INN-15).
- **Per-project and per-context setting.** The project object and each context object of [§11.1](#111-configuration-shape)
  gain an optional `"inner_agent": "off" | "local_only" | "inherit"` (default `inherit`). There is deliberately no `on`
  value: a project can only restrict what the installation-level configuration allows. The effective value is the most
  restrictive of project and context (`off` over `local_only` over `inherit`). Runs started by `workspace_path`, with no
  project, use `inherit`.
- Tasks are enabled individually and none is on by default (FR-INN-05). A task whose master switch, task switch, mode,
  privacy gate or suspension forbids the call uses its fallback (§13.7).

### 13.2 Backend port

```ts
type InnerTask = 'commit_message' | 'pr_draft' | 'route_features' | 'handoff_condense' | 'log_summary' | 'run_title';
type Locality = 'local' | 'remote';

interface InnerRequest {
  task: InnerTask;
  template_version: string;            // e.g. "commit_message.v1"; part of the task contract, bumped on any prompt change
  system: string;                      // fixed template text owned by the task contract, never built from input
  user: string;                        // redacted, budget-truncated input (§13.4 steps 2-3)
  max_output_tokens: number;
  response_schema: object;             // JSON Schema of the expected output; a hint to the backend, never trusted (§13.4)
}

interface InnerResult {
  text: string;                        // raw completion text; untrusted data (FR-INN-07)
  usage?: { in: number | null; out: number | null };   // as reported by the backend; null/absent = unknown, never estimated
  model_id: string;                    // as reported by the backend, else the configured model string
}

interface InnerBackend {
  readonly kind: 'http' | 'cli';
  resolveLocality(signal: AbortSignal): Promise<Locality>;   // at connect time, every connection (rule below)
  complete(req: InnerRequest, signal: AbortSignal): Promise<InnerResult>;   // rejects on transport/exit failure
  probe(signal: AbortSignal): Promise<{ reachable: boolean; canary_ok: boolean; eligible: boolean; detail: string }>;
}
```

The port carries one request and one answer. There is no tool, file, session, history or streaming parameter, so a
backend cannot be asked for more than a single completion (FR-INN-02). How `InnerRequest` maps onto a chat-completion
request body, whether `response_schema` is passed as a structured-output constraint, and how usage is read are **Proposed**
details of the `http` implementation, fixed in T11.3 against the endpoint the operator runs; the controller validates the
output the same way whether or not the backend honoured the schema.

**Kinds.**

- `http`: a chat-completion endpoint the operator runs or reaches (FR-INN-03). Model and endpoint come only from the
  configuration. No redirects are followed and no proxy environment variable is read (Proposed).
- `cli`: an installed provider CLI run once, headless, with an operator-chosen model, the first being `opencode run`
  (FR-INN-04, FR-ADP-08). **Proposed; flags unverified (Q-26, T11.0).** The run uses an empty temporary directory, a
  minimal environment (FR-EXE-07), no repository config, and only argv that passes the adapter argv audit (no bypass flag;
  [AGENTS.md](../../AGENTS.md)). The way the prompt is delivered (argv, stdin or file) and the output read are fixed by
  the T11.0 spike, not guessed here.

**Ineligible rule (cli).** The `cli` backend is `eligible` only if (a) the installed version is inside a compliance
manifest range (FR-ADP-03) and (b) the documented controls that offer the model no tools, no file and no shell access have
been shown to apply for that version (T11.0). Otherwise `probe` returns `eligible: false`, the backend is reported
`Ineligible` in `doctor`, no process is started, and every task uses its fallback. Nothing downgrades this to "run it
anyway".

**Locality classification** (FR-INN-16). `local` means the address the controller actually connects to is a loopback
address (`127.0.0.0/8`, `::1`) or a Unix domain socket on the host; everything else is `remote`.

- Resolved **at connect time, not only at config load**: for `http`, the hostname is resolved when the connection is made,
  the controller connects to that resolved address (so a second lookup cannot differ), and the peer address of the
  established socket is checked. A hostname resolving to several addresses is `local` only if every address is loopback.
  A name that was loopback at load but resolves elsewhere now is `remote` for that call; if `allow_remote` is false the
  call is denied (§13.5). A failure to resolve is `remote` (fail closed).
- The `cli` kind is always `remote` (Proposed): the controller cannot see where the installed CLI sends the prompt.
- The classification used for each call is stored in `inner_call.locality` and shown by `doctor`.

### 13.3 Data

Added by the M11 forward migration ([§1](#1-data-model)). Same conventions as §1: ULID text IDs with a prefix (`inc_`,
Proposed), UTC millisecond timestamps, `STRICT`, no prompt or response body in any column (FR-INN-16).

```sql
CREATE TABLE inner_call (               -- append-only (FR-INN-15, FR-INN-09); never usage_observation, never capacity
  id              TEXT PRIMARY KEY CHECK (id LIKE 'inc\_%' ESCAPE '\'),
  task            TEXT NOT NULL CHECK (task IN ('commit_message','pr_draft','route_features','handoff_condense',
                    'log_summary','run_title')),
  backend_kind    TEXT NOT NULL CHECK (backend_kind IN ('http','cli')),
  model_id        TEXT NOT NULL,        -- reported by the backend, else the configured model string
  locality        TEXT NOT NULL CHECK (locality IN ('local','remote')),
  template_version TEXT NOT NULL,
  outcome         TEXT NOT NULL CHECK (outcome IN ('accepted','rejected_validator','rejected_sanitiser',
                    'fallback_unavailable','fallback_suspended','fallback_disabled')),
  reason          TEXT,                 -- short code only (e.g. REMOTE_NOT_ALLOWED, CIRCUIT_OPEN, TIMEOUT); no free text
  attempts        INTEGER NOT NULL CHECK (attempts BETWEEN 0 AND 2),   -- 0 when no call was made; 2 after a re-ask
  latency_ms      INTEGER NOT NULL,     -- wall time of the whole pipeline attempt, 0 when no call was made
  tokens_in       INTEGER,              -- as reported; NULL = unknown (never estimated)
  tokens_out      INTEGER,
  input_bytes     INTEGER NOT NULL,     -- size of the redacted, budget-truncated user text actually sent
  output_bytes    INTEGER NOT NULL,     -- size of the raw completion received (0 if none)
  input_sha256    TEXT NOT NULL,        -- hash of that sent text; lets a test or operator match without storing it
  run_id          TEXT REFERENCES run(id),                 -- NULL for calls outside a run (inner test, doctor canary)
  meta_session_id TEXT REFERENCES meta_session(id),
  created_at      TEXT NOT NULL
) STRICT;
CREATE INDEX inner_call_task_time ON inner_call(task, created_at);
CREATE INDEX inner_call_run ON inner_call(run_id);

CREATE TABLE inner_task_state (         -- mutable current state, one row per task (FR-INN-09)
  task            TEXT PRIMARY KEY CHECK (task IN ('commit_message','pr_draft','route_features','handoff_condense',
                    'log_summary','run_title')),
  suspended       INTEGER NOT NULL DEFAULT 0 CHECK (suspended IN (0,1)),
  suspended_at    TEXT,
  suspended_basis_json TEXT CHECK (suspended_basis_json IS NULL OR json_valid(suspended_basis_json)), -- window, rejected, total, threshold
  resumed_at      TEXT,                 -- window counting restarts after this instant
  version         INTEGER NOT NULL DEFAULT 0
) STRICT;
```

`inner_call` gets the same `BEFORE UPDATE`/`DELETE` guards as the other append-only tables. The outcomes mean: `accepted`
(the output passed every check and was used); `rejected_validator` (not valid after the permitted re-ask);
`rejected_sanitiser` (valid, but the sanitiser left nothing usable); `fallback_unavailable` (the call could not be made
or completed: unreachable, timeout, error, open circuit, no free slot, `Ineligible`); `fallback_suspended` (the task is
suspended, §13.4 step 11); `fallback_disabled` (the task is enabled but a gate forbade the call: locality, `allow_remote`,
`allow_source_content`, project setting, or the backend switched off). A task that is simply not enabled, or a
`commit_message` call skipped because the agent supplied a message in `draft_if_missing`, writes no row.

The accepted result lives where it is used, not in `inner_call`: a commit message in the commit, a PR draft and condensed
text in artifacts, route features in `route_decision.features_json`, a run title in a `run_event` payload (§13.6). The
`usage_observation` exception for `shares_subscription_with` is in §13.4 step 13.

### 13.4 Call pipeline

One pipeline serves every task; the task contract (§13.6) supplies the input builder, template, schema, validator and
fallback. Redaction is the same component and rules as telemetry (FR-TEL-03, ADR-0012), not a second implementation.

1. **Gate.** If `enabled` is false or the task is not enabled, return the fallback with no row. If the task is suspended
   (`inner_task_state.suspended`), record `fallback_suspended` and return the fallback. Otherwise evaluate the privacy
   gates of §13.5; a denial records `fallback_disabled` with the reason code and returns the fallback. No bytes of task
   input are sent before this point; only name resolution for `resolveLocality` may occur.
2. **Build and redact.** The task's input builder takes typed controller-owned fields (never a run object, a transcript
   or a request body) and produces the text. Then, over every string in it, in this order: (a) the telemetry redactor
   (credential-like values, home paths, environment values), (b) the identifier scrub: the patterns of §12.4 rules
   `id.controller` and `id.native-session` and the configured provider names, so the prompt carries none of them
   (FR-INN-10), (c) control-character stripping. The redactors only remove or mask; nothing the model returns is ever fed
   back into them (FR-INN-06, FR-INN-18).
3. **Budget.** If the text exceeds `input_budget_bytes`, truncate deterministically, never in the middle of a UTF-8
   sequence, and insert a marker line `[truncated: <n> bytes omitted]`. Diffs: keep the file list and per-file stat header
   whole, then whole hunks in path order until the budget is used. Logs and long text: keep a head of 25% and a tail of
   75% of the budget (proposed target split). The marker and the fixed template are always kept. Truncation is recorded
   only through `input_bytes`.
4. **Hash.** `input_sha256` is computed over the text that will be sent.
5. **Slot.** Acquire the per-backend semaphore (`max_concurrency`) waiting no longer than the remaining per-call bound.
   No slot in time: `fallback_unavailable` (`BUSY`).
6. **Breaker.** `closed`: proceed. `open`: do not call; `fallback_unavailable` (`CIRCUIT_OPEN`). `half_open`: exactly one
   call at a time goes through as the probe; others see `open`. Transitions:
   - `closed` to `open` after `breaker.failure_threshold` consecutive transport-level failures (connect error, timeout,
     non-success response, unreadable response envelope, process failure for `cli`) across all tasks on the backend;
   - `open` to `half_open` after `breaker.open_ms`;
   - `half_open` to `closed` on a call that returns a transport-level success, to `open` on a failure.
   A validator or sanitiser rejection is a quality outcome, not a transport failure: it does not move the breaker. Breaker
   state is held in memory and starts `closed` at process start (Assumption; `doctor` re-probes).
7. **Call.** The deadline is `timeout_ms` (task value if lower) for the whole pipeline including a re-ask; the
   `AbortSignal` cancels the request or kills the `cli` process group at the deadline. The caller is never blocked longer.
8. **Decode and strip.** The raw text must be valid UTF-8 (otherwise invalid), is capped at the task's output byte limit
   (longer is invalid, not truncated), stripped of control characters other than newline and tab, and, for JSON tasks,
   parsed as a single JSON value with nothing else around it.
9. **Validate.** Ajv against the task's output schema (`additionalProperties: false`), then the task's validator rules
   (§13.6). On failure, **one re-ask** if time remains: the same request plus a fixed error class from a closed list
   (`not_json`, `schema`, `too_long`, `empty`, `rule`), never the rejected text, so hostile output is not echoed back. A
   second failure is `rejected_validator`.
10. **Sanitiser (commit_message and pr_draft only).** Run the [§12.4](#124-message-sanitisation) sanitiser unchanged over
    the text. Empty or unusable afterwards is `rejected_sanitiser`, with no re-ask. Sanitiser counts go to
    `git_commit.sanitizer_json` as for any message.
11. **Quality window and suspension.** Over the task's last `suspension.window_calls` calls with outcome `accepted`,
    `rejected_validator` or `rejected_sanitiser` since `inner_task_state.resumed_at` (`fallback_*` outcomes are not quality
    evidence and are not counted), if at least `suspension.min_calls` exist and the rejected share exceeds
    `suspension.rejection_threshold`, set `suspended = 1` in one transaction. The task then returns `fallback_suspended`
    until the operator re-enables it (FR-INN-09). The re-enable command, Proposed as `inner resume <task>`, is not in
    FR-INN-17's list: the SRS needs a note, or the re-enable becomes a config edit plus restart (unreconciled). Suspension
    never reverses a result already accepted.
12. **Accept or fall back.** Accepted: return the validated value to the caller, which performs every action that follows
    (FR-INN-02). Any rejection or failure: return the task's deterministic fallback (§13.7). In no case does the caller's
    run change state because of the result (FR-INN-08).
13. **Record.** In one ledger transaction: the `inner_call` row; for a call tied to a run, one `run_event` of kind
    `inner_call` (plus `inner_degraded` or `inner_task_suspended` when a transition happened, §13.8); and, only when
    `shares_subscription_with` names a provider, one `usage_observation` for that provider with `source = 'inner_agent'`
    and the reported token counts in `metrics_json` (empty when unknown). `provider_health`, the capacity estimator and
    `capacity_score` are not touched (FR-INN-15). Bodies are never written.

Every step is wrapped so that an exception inside the pipeline becomes `fallback_unavailable`; the pipeline has no code
path that throws into the run supervisor.

### 13.5 Privacy gates

Evaluated in step 1 of §13.4, before any task data leaves the process. "Source content" is repository-derived text:
diffs and file lists with hunks (`commit_message`, `pr_draft`), log or verification output excerpts (`log_summary`),
diff excerpts and decision text carried into a handoff (`handoff_condense`). `route_features` and `run_title` send the
request's objective text and counts only, which is not repository content; whether a remote backend should see an
objective without a second opt-in is an open point (Assumption: `allow_remote` alone is enough).

| # | Effective project setting | Backend locality | `allow_remote` | Task sends source content | Task `allow_source_content` | Result | Reason code |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | `off` | any | any | any | any | Denied | `PROJECT_OFF` |
| 2 | `local_only` | remote | any | any | any | Denied | `PROJECT_LOCAL_ONLY` |
| 3 | `local_only` or `inherit` | local | any | any | any | Allowed | n/a |
| 4 | `inherit` | remote | false | any | any | Denied | `REMOTE_NOT_ALLOWED` |
| 5 | `inherit` | remote | true | no | any | Allowed | n/a |
| 6 | `inherit` | remote | true | yes | false | Denied | `SOURCE_CONTENT_NOT_ALLOWED` |
| 7 | `inherit` | remote | true | yes | true | Allowed | n/a |

A denial is `fallback_disabled`. Further rules: `cli` is `remote` (§13.2), so rows 4 to 7 apply to it; an unresolved
locality is `remote`; an `Ineligible` backend is `fallback_unavailable` (`INELIGIBLE`), not a privacy result.
`inner test <task>` and the `doctor` canary use a built-in fixture with no repository data, so they are subject to
rows 4 and 5 only. In every allowed case redaction (§13.4 step 2) still runs, and bodies are still not logged (FR-INN-16).
`allow_source_content` is meaningless for a `local` backend (row 3) and is ignored there.

### 13.6 Task contracts

Each task has a versioned template (`<task>.v1`, Proposed), an input budget, an output schema, a validator and a
fallback (FR-INN-05). All output schemas use `additionalProperties: false`. All input builders **exclude**: controller,
session and run IDs, native provider session IDs, provider, adapter and model names, internal run-branch and publish-ref
names (they contain session IDs), absolute home paths, credentials, and the raw agent transcript. Paths are
worktree-relative. Output length limits are proposed targets.

| Task (`FR`) | Input fields | Output schema | Validator rules beyond the schema | Fallback |
| --- | --- | --- | --- | --- |
| `commit_message` (FR-INN-10) | Paths being committed; unified diff of exactly those paths; up to 5 recent subject lines of the publish ref (style hint); nothing else. The agent's own message is not sent, and neither is the objective | `{ "subject": string 1..72, "body"?: string 0..2000 }` | Subject is one line, no leading or trailing space, no control characters, no code fence; body has no `Co-authored-by`-style key line (the sanitiser also removes them); result = `subject` plus blank line plus `body` | No message: tool error `MESSAGE_REQUIRED` (§12.1); never an invented message |
| `pr_draft` (FR-INN-11) | Subjects of the controller-made commits on the publish ref since its base; changed file list with line counts; diff excerpt within budget; controller-computed verification facts (command label, pass or fail) if any | `{ "title": string 1..100, "body": string 1..8000 }` | Single-line title; markdown body; if the verification facts hold no pass, or hold a fail, the draft is rejected when it matches a success claim (for example "all tests pass"; pattern list Proposed); no URLs added (Proposed) | No `pr_draft` artifact; `get_artifacts` returns none and the orchestrator writes its own. Stored as artifact kind `pr_draft`, `application/json`, referenced by the `inner_call` run event |
| `route_features` (FR-INN-12) | Objective text (truncated); counts: constraints, verification commands, repository file count and size band, extension histogram; no trust profile, no `provider_preference`, no provider names | `{ "context_volume": "small"\|"medium"\|"large", "autonomy": "low"\|"medium"\|"high", "reasoning_depth": "low"\|"medium"\|"high", "task_kind": "bug_fix"\|"feature"\|"refactor"\|"test"\|"docs"\|"investigation"\|"other" }` | Enumerations only, no free text, all four keys present; stage-2 scoring input only, never read by eligibility or by `require_provider` handling | The heuristic classifier (FR-RTE-04); if it too is unavailable, the neutral value `medium` for each level and `other` |
| `handoff_condense` (FR-INN-13) | Labelled controller-owned text fields of the bundle (goal, constraints, decisions, failed-attempt notes, open tasks) and bounded diff excerpts; statuses, exit codes and counts are not sent | `{ "fields": { "<name>": string 1..600 } }`, names limited to the bundle's prose fields | Every key is a requested field; each value is no longer than its source field; every digit sequence in a value occurs in the source (no invented counts or codes); the bundle stores `{ text, source: "inner", model_id, template_version, raw_artifact_id, raw_sha256 }` per condensed field | Deterministic truncation of the raw text with a truncation marker; structured bundle fields are unchanged either way |
| `log_summary` (FR-INN-13) | Head and tail excerpt of the verification output or log artifact; controller facts as labelled lines (command label, exit code, counts) given as facts to restate, not infer | `{ "summary": string 1..600, "notable"?: string[] (max 5, each 1..160) }` | Same digit-in-source rule; no sentence may be the only carrier of a status: the envelope's `status`, exit codes and counts come from records, not from this text; stored with source label and raw artifact ID plus hash | Deterministic head and tail excerpt with line and byte counts, labelled `source: heuristic` |
| `run_title` (FR-INN-14, Could) | First N characters of the objective (within budget) | `{ "title": string 1..80, "summary"?: string 1..200 }` | Single line each, no control characters, no markdown, no URLs; treated as data in every listing | First line of the objective truncated to 80 characters. Accepted values go in a `run_event` payload of kind `inner_call` (Proposed; no run-table column) |

The `commit_message` task modes (FR-INN-10): `draft_if_missing` draws on the inner agent only when the agent supplied no
message; `always` requests a draft in every commit and uses it when valid, otherwise the agent's message if present;
`never` disables the task for commits and keeps `message` required. A route feature is stored in
`route_decision.features_json` as `{ "value": ..., "source": "heuristic" | "inner", "model_id"?: string,
"template_version"?: string }` per feature; replay reads the stored value and never calls the model (FR-RTE-03,
FR-INN-12). Handoff and log text always carry a visible source label so a reader can tell inner prose from controller
facts.

### 13.7 Fallback table

| Situation | `inner_call.outcome` | Result for the caller |
| --- | --- | --- |
| Inner agent not configured, `enabled: false`, task not enabled, or `commit_message` supplied by the agent in `draft_if_missing` | No row | Task fallback; behaviour identical to a build with no inner agent |
| A privacy gate or project setting forbids the call (§13.5) | `fallback_disabled` (reason code) | Task fallback |
| Task suspended after a high rejection rate | `fallback_suspended` | Task fallback until the operator resumes the task |
| Backend unreachable, timeout, error response, open circuit, no free slot, `Ineligible` cli | `fallback_unavailable` (reason code) | Task fallback within the per-call bound; `doctor` shows degraded |
| Output invalid after at most one re-ask | `rejected_validator` | Task fallback |
| Commit or PR text empty or unusable after the sanitiser | `rejected_sanitiser` | Task fallback |
| Output accepted | `accepted` | The validated value |

| Task | Deterministic fallback |
| --- | --- |
| `commit_message` | Tool error `MESSAGE_REQUIRED`; the agent writes the message. Under `always`, the agent's own message when it supplied one |
| `pr_draft` | No artifact |
| `route_features` | Heuristic classifier features, else neutral values |
| `handoff_condense` | Deterministically truncated raw text, labelled |
| `log_summary` | Head and tail excerpt with counts, labelled |
| `run_title` | First line of the objective, truncated |

No fallback depends on a second model call, and no fallback changes a run's state, exit code or verification result.

### 13.8 Telemetry and events

**Span `inner.call`** (added to [§7](#7-telemetry-spans)): one per pipeline run that reaches step 5 or later, parent
`controller.delegate` for a run-linked call, else a root span. Allowed attributes (by construction, no bodies,
ADR-0012): `inner.task`, `inner.backend_kind`, `inner.locality`, `inner.template_version`, `inner.model` (the model ID as
reported or configured), `inner.outcome`, `inner.reason` (short code), `inner.attempts`, `inner.latency_ms`,
`inner.input_bytes`, `inner.output_bytes`, `inner.tokens_in`, `inner.tokens_out` (only when reported),
`inner.breaker_state`, and, for run-linked calls, `run.id` and `session.id`. Forbidden: the prompt, the response, the diff,
log excerpts, objective text, any message text, the backend URL's userinfo. The exporter drops every attribute not on this
list, and a test asserts it.

**Run events** (append-only `run_event.type`, bounded payloads, no text, M11), written only for calls tied to a run:

| Kind | Payload | When |
| --- | --- | --- |
| `inner_call` | `inner_call_id`, `task`, `outcome`, `reason?`, `locality`, `template_version`, `attempts`, `latency_ms`, `input_bytes`, `output_bytes`; `artifact_id` column set for a `pr_draft` or condensed-text artifact; a `run_title` payload also carries `title` and `summary` (bounded) | Every recorded call |
| `inner_degraded` | `state` (`degraded` or `recovered`), `reason`, `breaker_state`, `backend_kind` | Breaker changes state, or an `Ineligible` probe result changes; written once per transition, not per failed call |
| `inner_task_suspended` | `task`, `window_calls`, `rejected`, `total`, `threshold` | A task is suspended (§13.4 step 11). A resume writes no event; `inner_task_state.resumed_at` records it |

Calls with no run (`inner test`, the `doctor` canary) have no `run_event`; their record is the `inner_call` row, and
`doctor` and `inner status` read `inner_call` and `inner_task_state`. None of these events or outcomes is a run failure
code, appears in an envelope's `failure_code`, or influences retry (§4).
